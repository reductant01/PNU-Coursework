## 1. 개념·OX (Part 2 PDF)

### 1-1
**묻는 것:** 스테이징 취소(unstage) 후 파일 내용

`readme.txt`를 `git add`한 뒤, 커밋 **전에** 스테이징만 취소했다.  
작업 폴더의 수정 내용은?

**정답:** **그대로 남는다** (unstage만 함, 수정은 버리지 않음)

**해설:** PDF "Unstaging a Staged File". `git reset HEAD readme.txt`는 스테이징에서만 내립니다. 수정을 버리려면 `git checkout -- readme.txt`(5-1·5-2)를 씁니다.

---

### 1-2
**묻는 것:** `git fetch` vs `git pull`

**정답:**  
- **`fetch`** — 원격의 최신 정보를 **가져오기만** 함 (자동 merge 없음)  
- **`pull`** — **fetch + merge** (가져와서 현재 브랜치에 합침)

**해설:** 5-1·`history 6.sh`의 `git fetch`와 동일. pull이 더 “한 번에 맞추기”입니다.

---

### 1-3
**묻는 것:** Git **태그(tag)** 의 두 종류 — Lightweight / Annotated

**문제:**  
(1) **Lightweight tag**가 무엇인지 한 줄로 쓰시오.  
(2) **Annotated tag**가 무엇인지 한 줄로 쓰시오.  
(3) Annotated tag를 만들 때 쓰는 대표 옵션은?

**정답:**  
(1) 특정 **commit을 가리키는 이름(북마크)** 만 붙인 것 (추가 정보 거의 없음)  
(2) **작성자·날짜·메시지** 등이 들어 있는 **공식 기록용** 태그  
(3) **`-a`** (보통 **`-m "메시지"`** 와 함께)

**해설:**

| 구분 | 만드는 방법 (예) | 시험용 한 줄 |
|------|------------------|--------------|
| **Lightweight** | `git tag v1.0` | commit에 **이름만** 붙임 |
| **Annotated** | `git tag -a v1.0 -m "Release 1.0"` | **릴리스 메모**가 있는 태그 |

- **비유:** Lightweight = 포스트잇에 “여기 v1.0”, Annotated = **릴리스 노트가 붙은 라벨**
- **시험 포인트:** `-a` 없이 `git tag 이름` → lightweight / `-a -m` → annotated (PDF Part2 슬라이드 11~12)
- **push:** 둘 다 기본 `git push`만으로는 안 올라갈 수 있음 → `git push origin v1.0` 또는 `--tags` (1-4 참고)

---

### 1-4
**묻는 것:** `git push`만 하면 태그도 원격에 올라가는가? ( O / X )

**정답:** **X**

**해설:** PDF "Sharing Tags". 기본 `git push`는 **브랜치 commit** 위주입니다. 태그는 **`git push origin <태그명>`** 또는 **`git push origin --tags`** 로 **별도로** 올립니다.

---

### 1-5
**묻는 것:** `git checkout v1.0` (태그) 후 상태

**정답:** **detached HEAD** 상태가 된다. (특정 commit/태그를 직접 가리킴, 브랜치 끝이 아님)

**해설:** PDF "Checking out Tags". 시험에서는 “태그 시점의 스냅샷으로 이동” 정도만 알아도 됩니다.

## 2. 명령·옵션 빈칸 채우기

> **「이런 일을 하려고 할 때, 빈칸에 뭐가 들어가야 할까?」**

---

### 2-1 (Unstaging)
**상황:** `report.txt`를 `git add`까지 했는데, commit 전에 **스테이징만 취소**하고 싶다. (파일 수정은 유지)

**문제:** 빈칸을 채우시오.

```bash
git reset HEAD ______ report.txt
```

**정답:** `--`

**해설:** 5-1·5-2와 동일. `reset HEAD -- 파일` = unstage.

---

### 2-2 (Showing remotes)
**상황:** 등록된 원격 저장소 **이름만** 목록으로 보고 싶다.

**문제:** 빈칸에 들어갈 하위 명령은?

```bash
git ______
```

**정답:** `remote`

**해설:** PDF "Showing Your Remotes". 보통 `origin` 등이 출력됩니다.

---

### 2-3
**상황:** 원격 **이름과 URL**을 함께 보고 싶다.

**문제:** 빈칸에 들어갈 옵션은?

```bash
git remote ______
```

**정답:** `-v`

**해설:** **verbose**. 예: `origin  https://bitbucket.org/... (fetch)` / `(push)`

---

### 2-4 (Adding remote)
**상황:** 새 원격 저장소 URL을 **`upstream`** 이라는 별칭으로 등록한다.

**문제:** 빈칸을 채우시오.

```bash
git remote ______ upstream https://github.com/user/repo.git
```

**정답:** `add`

**해설:** 5-2의 `git remote add origin <URL>`과 같습니다. 별칭만 `upstream`으로 바뀐 예입니다.

---

### 2-5 (Fetching)
**상황:** `origin`에 올라온 최신 commit 정보를 **로컬에만** 받고, 작업 폴더는 아직 자동으로 합치지 않는다.

**문제:** 빈칸을 채우시오.

```bash
git ______ origin
```

**정답:** `fetch`

**해설:** PDF "Fetching and Pulling from Your Remotes". 이후 merge는 `git merge` 또는 `git pull`로 합니다.

---

### 2-6 (Pulling)
**상황:** `origin`의 `master` 내용을 가져와 **현재 브랜치에 병합**한다.

**문제:** 빈칸을 채우시오.

```bash
git ______ origin master
```

**정답:** `pull`

**해설:** 5-1·5-2와 동일. fetch + merge를 한 번에.

---

### 2-7 (Pushing)
**상황:** 로컬 `master`의 commit을 원격 `origin`에 올린다.

**문제:** 빈칸을 채우시오.

```bash
git ______ origin master
```

**정답:** `push`

**해설:** PDF "Pushing to Your Remotes".

---

### 2-8 (Inspecting remote)
**상황:** `origin` 원격의 URL, 추적 브랜치 등 **자세한 정보**를 본다.

**문제:** 빈칸을 채우시오.

```bash
git remote ______ origin
```

**정답:** `show`

**해설:** PDF "Inspecting a Remote".

---

### 2-9 (Removing remote)
**상황:** 더 이상 쓰지 않는 원격 **`old-origin`** 등록을 삭제한다.

**문제:** 빈칸을 채우시오. (`remove` 또는 `rm`)

```bash
git remote ______ old-origin
```

**정답:** `remove` (또는 `rm`)

**해설:** PDF "Removing and Renaming Remotes". 로컬 설정에서만 사라지며, Bitbucket/GitHub 서버 자체가 지워지지는 않습니다.

---

### 2-10 (Renaming remote)
**상황:** 원격 별칭 `origin`을 **`upstream`** 으로 바꾼다.

**문제:** 빈칸을 채우시오.

```bash
git remote ______ origin upstream
```

**정답:** `rename`

**해설:** PDF "Removing and Renaming Remotes". 이후 push는 `git push upstream master`처럼 **새 이름**을 씁니다.

---

### 2-11 (Annotated tag)
**상황:** 현재 HEAD에 **릴리스 메시지**를 남기는 태그 `v1.0`을 만든다.

**문제:** 빈칸을 채우시오.

```bash
git tag ______ v1.0 ______ "Release 1.0"
```

**정답:** `-a` / `-m`

**해설:** PDF "Annotated Tags". `-a` = annotate, `-m` = message (commit의 `-m`과 비슷).

---

### 2-12 (Lightweight tag)
**상황:** 특정 commit에 **이름만** 붙이는 가벼운 태그 `v0.9`를 만든다. (메타데이터 없음)

**문제:** 빈칸에 들어갈 옵션은? (없음이면 **없음**이라고 쓰시오.)

```bash
git tag ______ v0.9
```

**정답:** **옵션 없음** (`git tag v0.9` 만)

**해설:** PDF "Lightweight Tags". `-a`, `-m` 없이 태그 이름만 주면 lightweight입니다.

---

### 2-13 (Tagging later)
**상황:** **과거 commit** `a1b2c3d`에 annotated 태그 `v0.1`을 붙인다.

**문제:** 빈칸을 채우시오.

```bash
git tag -a v0.1 ______ -m "First release"
```

**정답:** `a1b2c3d` (또는 해당 commit ID / HEAD~1 등)

**해설:** PDF "Tagging Later". 마지막 인자로 **태그를 붙일 commit**을 지정합니다.

---

### 2-14 (Sharing tags)
**상황:** 로컬에 만든 태그 **`v1.0` 하나만** 원격 `origin`에 올린다.

**문제:** 빈칸을 채우시오.

```bash
git push ______ v1.0
```

**정답:** `origin`

**해설:** PDF "Sharing Tags". `git push origin v1.0`.

---

### 2-15
**상황:** 로컬의 **모든 태그**를 원격에 한 번에 올린다.

**문제:** 빈칸을 채우시오.

```bash
git push origin ______
```

**정답:** `--tags`

**해설:** PDF "Sharing Tags". `git push`만으로는 태그가 안 올라가는 경우(1-4)와 짝입니다.

---

### 2-16 (Checking out tag)
**상황:** 태그 **`v1.0`이 가리키는 시점**의 파일 상태로 작업 폴더를 맞추고 싶다.

**문제:** 빈칸을 채우시오.

```bash
git ______ v1.0
```

**정답:** `checkout`

**해설:** PDF "Checking out Tags". 브랜치 이동과 같은 `checkout`이지만, 대상이 **태그(특정 commit)** 입니다.

---

### 2-17 (Git alias)
**상황:** `git status` 대신 **`git st`** 만 쳐도 되게 전역 별칭을 만든다.

**문제:** 빈칸을 채우시오.

```bash
git config --global ______.st status
```

**정답:** `alias`

**해설:** PDF "Git Aliases". `git st` → `git status` 실행. `alias.unstage "reset HEAD --"` 같은 것도 같은 방식입니다.

## 3. 결과 예측

### 3-1
**상황:** `git add file.txt` 후 `git reset HEAD file.txt` 실행. **작업 폴더의 file.txt 내용은 수정된 채**이다.

**문제:** `git status`에서 `file.txt`는 어느 섹션에 나오는가?  
(`Changes to be committed` / `Changes not staged for commit` / 없음)

**정답:** **Changes not staged for commit** (modified)

**해설:** staged → unstaged로만 내려갔고, 수정 내용은 작업 폴더에 남습니다. 5-2·5-3 Unstaging 시나리오입니다.

---

### 3-2
**상황:** 원격에 새 commit이 있는데, **`git fetch origin`만** 실행했다.

**문제:** 작업 폴더의 소스 파일이 **자동으로 바뀌었는가?** (O/X)  
`git merge` 또는 `git pull`이 **추가로** 필요한가? (O/X)

**정답:** **X** / **O**

**해설:** fetch는 **정보 다운로드** 위주입니다. 현재 브랜치에 반영하려면 merge(또는 pull)가 필요합니다.

---

### 3-3
**상황:** `git tag v2.0` (옵션 없음) 후 `git show v2.0`을 실행했다.

**문제:** annotated 태그처럼 **tagger 이름·태그 메시지 블록**이 **많이** 보이는가? (O/X)

**정답:** **X**

**해설:** lightweight 태그는 **commit 내용 위주**로 보이는 경우가 많습니다. annotated는 `-a -m`으로 메타데이터가 붙습니다.

---

### 3-4
**상황:** `git commit`까지 했고, `git tag -a v1.0 -m "release"`까지 했다. **`git push origin master`만** 실행했다.

**문제:** 원격에 **태그 v1.0**도 올라갔는가? (O/X)

**정답:** **X**

**해설:** 1-4, 2-14, 2-15. 태그는 **`git push origin v1.0`** 또는 **`git push origin --tags`** 가 필요합니다.

## 4. 순서·비교

### 4-1
**상황:** 원격 저장소를 처음 연결한 뒤, 남의 변경을 받아 오고, 내 변경을 올리는 **안전한** 순서.

**문제:** 아래를 올바른 순서로 번호 매기시오.

```
( ) git push origin master
( ) git remote add origin <URL>
( ) git pull origin master
( ) git commit -m "my work"
( ) git add .
```

**정답:**  
1. `git remote add origin`  
2. `git add .`  
3. `git commit`  
4. `git pull origin master`  
5. `git push origin master`

**해설:** 5-1·5-2와 같이 **commit → pull → push**. remote add는 맨 처음(또는 init 직후)에 한 번.

---

### 4-2
**문제:** `git remote` / `git remote -v` / `git remote show origin` — 각각 한 줄로 차이를 쓰시오.

**정답:**  
- **`git remote`** — 등록된 원격 **이름** 목록  
- **`git remote -v`** — 이름 + **URL** (fetch/push)  
- **`git remote show origin`** — `origin` 원격의 **상세 정보** (URL, 추적 브랜치 등)

**해설:** 세 명령 모두 **원격(GitHub/Bitbucket) 연결 정보를 보는** 명령입니다. 파일·스테이징과는 **무관**합니다.

**공통 전제:** `git remote add origin https://github.com/user/repo.git` 로 **한 번 등록해 둔 뒤** 아래처럼 확인합니다.

---

**① `git remote` — 이름만**

```bash
git remote
```

```
origin
```

| 알 수 있는 것 | 알 수 없는 것 |
|---------------|---------------|
| 원격 **별칭**이 `origin` 하나 있다 | **URL**이 뭐인지 |
| | fetch/push 주소 차이 |

→ **“연결된 원격 이름이 뭐지?”** 만 빠르게 볼 때

---

**② `git remote -v` — 이름 + URL**

```bash
git remote -v
```

```
origin  https://github.com/user/repo.git (fetch)
origin  https://github.com/user/repo.git (push)
```

| `-v` | verbose(자세히) |
|------|-----------------|
| `(fetch)` | `git pull` / `git fetch` 할 때 쓰는 주소 |
| `(push)` | `git push` 할 때 쓰는 주소 |

→ **“origin이 실제로 어느 주소를 가리키지?”** 볼 때 (5-3 §2-3)

---

**③ `git remote show origin` — origin 하나 상세**

```bash
git remote show origin
```

```
* remote origin
  Fetch URL: https://github.com/user/repo.git
  Push  URL: https://github.com/user/repo.git
  HEAD branch: main
  Remote branch:
    main tracked
  Local branch configured for 'git pull':
    main merges with remote main
  Local ref configured for 'git push':
    main pushes to main (up to date)
```

| 추가로 보이는 것 | 의미 |
|------------------|------|
| Fetch/Push URL | 주소 (②와 비슷) |
| HEAD branch | 원격 **기본 브랜치** (main 등) |
| Remote branch | 원격에 있는 브랜치 |
| Local branch … pull/push | 내 브랜치와 **어떻게 연결**돼 있는지 |

→ **“origin과 내 main이 pull/push에서 어떻게 맞물리지?”** 까지 볼 때 (5-3 §2-8 Inspecting)

---

**한눈에 비교**

| 명령 | 출력량 | 시험용 한 줄 |
|------|--------|--------------|
| `git remote` | **이름만** | 원격 목록 |
| `git remote -v` | 이름 + **URL** | 주소까지 |
| `git remote show origin` | URL + **브랜치·연결 정보** | origin **상세** |

**기억법:** 짧게 → `-v` → `show` 순으로 **점점 자세해짐**

## 5. 표 완성 (Part 2 핵심)

**문제:** 설명 칸을 채우시오.

| 명령 | 설명 (빈칸) |
|------|-------------|
| `git reset HEAD -- <file>` | |
| `git remote -v` | |
| `git fetch origin` | |
| `git pull origin master` | |
| `git push origin master` | |
| `git tag -a v1.0 -m "msg"` | |
| `git tag v1.0` | |
| `git push origin --tags` | |
| `git config --global alias.st status` | |

---

**정답·해설**

| 명령 | 비교·대상 | 설명 (시험에 적을 분량) |
|------|-----------|-------------------------|
| `git reset HEAD -- <file>` | 스테이징 → 작업 폴더만 | **unstage** (수정 내용은 유지) |
| `git remote -v` | 원격 목록 | 원격 **이름과 URL** 출력 |
| `git fetch origin` | 로컬 ← 원격 정보 | 원격 갱신 정보 **가져오기만** (자동 merge X) |
| `git pull origin master` | 로컬 ↔ 원격 | **가져와 병합** (fetch + merge) |
| `git push origin master` | 로컬 → 원격 | 로컬 commit을 **origin/master**에 업로드 |
| `git tag -a v1.0 -m "msg"` | HEAD(또는 지정 commit) | **annotated** 태그 생성 |
| `git tag v1.0` | HEAD(또는 지정 commit) | **lightweight** 태그 생성 |
| `git push origin --tags` | 로컬 태그 → 원격 | **모든 로컬 태그**를 origin에 push |
| `git config --global alias.st status` | 설정 | `git st` = **`git status` 별칭** |

**한 줄 답만 외울 때**

| 명령 | 한 줄 |
|------|--------|
| `reset HEAD -- file` | unstage |
| `remote -v` | 원격 이름+URL |
| `fetch` | 받기만 |
| `pull` | 받고+합치기 |
| `push` | 올리기 |
| `tag -a` | annotated 태그 |
| `tag` (옵션 없음) | lightweight 태그 |
| `push --tags` | 태그 전부 push |
| `alias.st` | status 줄임 명령 |

## 6. 종합 (시험 스타일)

**상황:** 아래를 순서대로 실행했다.

```bash
git add plan.txt
git reset HEAD -- plan.txt
git remote -v
git tag -a v1.0 -m "release"
git push origin master
```

**문제:**  
(1) `plan.txt`는 스테이징 영역에 있는가? (O/X)  
(2) `git remote -v`는 **파일 diff**를 보여 주는가? (O/X)  
(3) `v1.0` 태그는 **annotated** 인가, **lightweight** 인가?  
(4) 위만으로 원격에 **태그 v1.0**이 올라갔는가? (O/X)

**정답:**  
(1) **X**  
(2) **X**  
(3) **annotated**  
(4) **X**

**해설:**  
(1) reset으로 unstage → staged 아님, 수정은 working에 남을 수 있음  
(2) remote -v = 원격 URL 목록  
(3) `-a -m` 사용  
(4) 태그 push 별도 필요 (`git push origin v1.0` 또는 `--tags`)

## 자주 헷갈리는 것 (5-3)

| 헷갈림 | 정리 |
|--------|------|
| `reset HEAD --` vs `checkout --` | unstage vs 수정 **폐기** |
| `fetch` vs `pull` | 받기만 vs 받고+merge |
| `push` vs `push --tags` | 브랜치 commit vs **태그** |
| `tag` vs `tag -a` | lightweight vs annotated |
| `remote add` vs `git add` | **URL 등록** vs **파일 스테이징** |
| `remote remove` | 로컬 별칭 삭제 (서버 repo 삭제 아님) |
