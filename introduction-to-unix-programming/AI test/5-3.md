## 유형 1. 개념 O/X

> **목표:** 틀리면 안 되는 **개념**부터 잡기. ( O / X )

---

### 1-1
**문제:** `git reset HEAD -- file`로 unstage한 뒤, 작업 폴더의 **수정 내용은 그대로** 남는다. ( O / X )

**정답:** **O**

**해설:** unstage만 함. 수정을 버리려면 `git checkout -- file`(5-1·5-2).

---

### 1-2
**문제:** `git fetch`는 원격 정보만 받고, `git pull`은 받은 뒤 **merge까지** 한다. ( O / X )

**정답:** **O**

**해설:** `pull` ≈ `fetch` + `merge`.

---

### 1-3
**문제:** `git push`만 실행하면 로컬 태그도 **자동으로** 원격에 올라간다. ( O / X )

**정답:** **X**

**해설:** 기본 push는 **브랜치 commit** 위주. 태그는 `git push origin <태그명>` 또는 `--tags`로 **별도** push.

---

### 1-4 (태그 checkout · detached HEAD)
**상황:** 프로젝트에 **태그** `v1.0` 이 있음 (예: `git tag v1.0` 으로 **1.0 릴리스 commit** 에 이름표 붙임).

```bash
git checkout v1.0
```

**문제:** 위처럼 **태그**로 checkout 하면 **detached HEAD** 상태가 된다. ( O / X )

**정답:** **O**

**해설:**

**`v1.0`(태그)** = 특정 commit 에 붙인 **이름표** (버전 표시 · `2-11`).

**`git checkout v1.0`** = 그 **commit 시점**으로 이동 (과거 1.0 버전 **코드 보기**).

**HEAD** = “지금 서 있는 commit” 포인터 (`5-1` `1-6`).

| checkout 대상 | HEAD 가 가리키는 곳 | 상태 |
|---------------|---------------------|------|
| **`main`** (브랜치) | **브랜치 끝** commit | **attached** (정상) |
| **`v1.0`** (태그) | **commit 하나** (브랜치 끝 **아님**) | **detached HEAD** |

**detached HEAD** = HEAD 가 **브랜치가 아니라 commit 에 직접** 붙음 · “**떠 있는**” 상태.

```
main:     A — B — C  ← HEAD(보통 main 끝)
tag v1.0:      ↑ B 에 붙음

git checkout v1.0  →  HEAD 가 B 를 **직접** 가리킴 (main 과 **분리**)
```

→ 여기서 commit 하면 **브랜치에 안 쌓일 수 있음** · 보통 **과거 버전 열람**용 · 돌아오려면 `git checkout main`.

---

### 1-5
**문제:** `git reset HEAD -- file`은 **unstage**, `git checkout -- file`은 **작업 폴더 수정 폐기**다. ( O / X )

**정답:** **O**

**해설:** reset = 스테이징만 취소 · checkout `--` = 마지막 commit 상태로 되돌림.

---

### 1-6
**문제:** `git fetch origin`만 하면 현재 브랜치에 **자동 merge**된다. ( O / X )

**정답:** **X**

**해설:** fetch = **정보 다운로드**만. 반영하려면 `merge` 또는 `pull` 추가.

---

### 1-7
**문제:** `git push origin --tags`는 로컬의 **모든 태그**를 원격에 올린다. ( O / X )

**정답:** **O**

**해설:** `push`만 = 브랜치 commit · `push --tags` = **태그** 별도 반영.

---

### 1-8 (lightweight vs annotated tag)
**상황:** 같은 commit 에 태그를 두 가지 방식으로 붙일 수 있음 (`2-11`·`2-12`).

```bash
git tag v1.0                          # lightweight
git tag -a v1.0 -m "Release 1.0"     # annotated
```

**문제:** 위처럼 **옵션 없음** = lightweight · **`-a` `-m`** = annotated 태그다. ( O / X )

**정답:** **O**

**해설:**

| 옵션 | 축약 | 역할 |
|------|------|------|
| **`-a`** | **a**nnotated | **annotated 태그**로 만듦 (작성자·날짜·메시지 **기록**) |
| **`-m`** | **m**essage | 태그 **설명 문자열** (`commit -m` 과 같음 · `5-1`) |

| 종류 | 명령 | 특징 |
|------|------|------|
| **lightweight** | `git tag v1.0` | commit 에 **이름만** 붙임 · 가벼움 |
| **annotated** | `git tag -a v1.0 -m "msg"` | **릴리스용** · `git show v1.0` 에 tagger·메시지 **더 많이** 보임 (`1-11`) |

→ **`-a`** = “자세한 태그로” · **`-m`** = “태그 메시지 적기”.

---

### 1-9 (`remote add` vs `add`)
**상황:** GitHub repo URL 을 내 PC Git 에 연결한 뒤 push (`3-2` · `history 6.sh`).

```bash
git remote add origin https://github.com/user/repo.git
git push -u origin main
```

**문제:** `git remote add`는 **URL 등록**, `git add`는 **파일 스테이징**이다. ( O / X )

**정답:** **O**

**해설 — remote 가 뭐야?**

**remote(원격)** = GitHub/Bitbucket 같은 **서버 저장소** · 내 PC **밖**에 있는 repo.

**`git remote add origin <URL>`** = 서버 주소를 **내 PC `.git` 설정에 적어 두는 것**.

```
[내 PC .git]  안에 메모장 한 줄:
  origin = https://github.com/user/repo.git
           ↑ 별칭 이름    ↑ 실제 URL
```

→ **URL이 “원격 서버에 등록”되는 게 아님** · **내 PC가 “이 주소를 origin 이라 부르자”** 고 **기록**하는 것 (`5-1` `3-2`).

**`push` 까지 흐름:**

| 단계 | 명령 | 어디서 |
|------|------|--------|
| 주소 **등록** | `remote add origin <URL>` | **내 PC** 설정만 |
| **업로드** | `push origin main` | 내 PC → **서버** |

**`git add` 와 이름만 비슷:**

| 명령 | 대상 | 하는 일 |
|------|------|---------|
| **`git add`** | **파일** | 작업 폴더 → **스테이징** |
| **`git remote add`** | **URL** | GitHub 주소 → **내 PC remote 목록** |

**왜 `remote remove` 로 서버가 안 지워지나?** (`1-10`)

`remove` = **내 PC 메모장에서 `origin` 줄만 지움** · 서버 repo / 브랜치 / commit 은 **손대지 않음**.

→ 서버 삭제 = **웹** · 원격 브랜치 = `push origin --delete` · 별칭만 = `remote remove`.

---

### 1-10
**문제:** `git remote remove origin`은 Bitbucket/GitHub **서버 저장소 자체**를 삭제한다. ( O / X )

**정답:** **X**

**해설:** `git remote remove origin` = 내 PC에서 **`origin` 이라는 주소 별칭만** 지움 · GitHub/Bitbucket **서버 repo 는 그대로**.

| 하고 싶은 일 | 명령 |
|--------------|------|
| 로컬 **원격 별칭** 삭제 | `git remote remove origin` (이 문제) |
| **원격 브랜치** 삭제 | `git push origin --delete 브랜치명` (`5-4`) |
| **로컬 브랜치** 삭제 | `git branch -d 브랜치명` (`5-4`) |
| **서버 저장소 전체** 삭제 | Git 웹에서 삭제 (Git 명령 **아님**) |

```bash
git push origin --delete old-feature   # origin 의 old-feature 브랜치만 삭제
```

→ **remote remove** ≠ 원격 브랜치 삭제 ≠ 서버 repo 삭제.

---

### 1-11
**문제:** `git show v2.0`에서 `git tag v2.0`(lightweight)은 annotated처럼 **tagger·태그 메시지 블록**이 많이 보인다. ( O / X )

**정답:** **X**

**해설:** lightweight = **commit 내용 위주** · annotated = `-a -m` 메타데이터.

---

### 1-12 (`git tag` · 목록 보기)
**상황:** 프로젝트에 태그가 몇 개 있음:

```bash
git tag v0.9              # lightweight
git tag -a v1.0 -m "Release 1.0"   # annotated
```

**문제:** 이미 붙어 있는 태그 **이름만** 보려면 `git tag`(옵션 없이) 로 **목록**을 볼 수 있다. ( O / X )

**정답:** **O**

**해설:**

**태그** = commit 에 붙인 **버전 이름표** (`v1.0` 등 · `1-4`).

**`git tag` (옵션 없음)** = **등록된 태그 이름 나열** (만드는 명령이 **아님**).

```bash
git tag
# v0.9
# v1.0
```

→ **lightweight**·**annotated** 구분 없이 **이름만** 출력.

| 명령 | 하는 일 |
|------|---------|
| **`git tag`** | 태그 **목록 보기** (이 문제) |
| **`git tag v1.0`** | 태그 **만들기** (lightweight · `2-12`) |
| **`git tag -a v1.0 -m "msg"`** | 태그 **만들기** (annotated · `1-8`) |
| **`git show v1.0`** | 태그 **내용** 자세히 보기 |

**헷갈림:** `-a` 는 **목록 볼 때** 쓰는 게 **아님** · **만들 때**만 annotated 로 씀 (`1-8`).

### 2-17 (Git alias)
**상황:** `git status` 대신 **`git st`** 만 쳐도 되게 전역 별칭을 만든다.

```bash
git config --global ______.st status
```

**정답:** `alias`

**해설:**

**전체 명령:**

```bash
git config --global alias.st status
#                   ↑      ↑   ↑
#                 alias  이름  실제로 실행할 명령
```

→ 이후 **`git st`** = **`git status`** 와 같음.

**왜 `alias.st` 인가? · `.` 역할**

`git config` 키는 **`섹션.이름`** 형식 · **`.`** = **구분자**(계층).

| 키 | 의미 |
|----|------|
| **`alias`** | “Git **별칭** 모음” **섹션** |
| **`alias.st`** | 그 안의 **`st`** 라는 별칭 하나 |
| 값 `status` | `git st` 치면 **`status` 실행** |

→ `user.name` · `user.email` 도 같은 패턴 (`user` 섹션 · `name` 항목).

**`git status` 옵션** (이 별칭은 **옵션 없는** status · `5-1`):

| 옵션 | 뜻 |
|------|-----|
| **(없음)** | 파일·브랜치·**ahead/behind** 등 **자세히** (`5-5`) |
| **`-s`** | **short** · 파일만 한 줄 (`??` ` M` … · `1-7`) |
| **`-sb`** | `-s` + **브랜치·원격 비교** (`-b` = branch) |

별칭을 `status -s` 로 잡으면 `git st` 가 **짧은 형식**이 됨 · 이 문제는 **`status` 그대로**.

| `git fetch origin` | |
| `git pull origin master` | |
| `git push origin master` | |
| `git tag -a v1.0 -m "msg"` | |
| `git tag v1.0` | |
| `git push origin --tags` | |
| `git config --global alias.st status` | |

**정답:** unstage (수정 유지) / 원격 **이름+URL** / 원격 정보 **가져오기만** / **가져와 병합** / 로컬 commit **업로드** / **annotated** 태그 / **lightweight** 태그 / **모든 태그** push / `git st` = status **별칭**

### 2-19 (alias.unstage)
**상황:** `git reset HEAD --`를 **`git unstage file`** 로 줄이려면?

```bash
git config --global alias.unstage "______"
```

**정답:** `reset HEAD --`

**해설:**

```bash
git config --global alias.unstage "reset HEAD --"
```

→ **`git unstage file`** 실행 시 **`git reset HEAD -- file`** 과 같음.

**`"` 가 왜 필요?**

값에 **공백**이 있어서 · 쉘이 **한 덩어리**로 넘기려면 따옴표 필요.

| 입력 | `alias.unstage` 에 저장되는 값 | 결과 |
|------|-------------------------------|------|
| **`"reset HEAD --"`** (정답) | `reset HEAD --` **전체** | `git unstage file` **정상** |
| **따옴표 없음** `reset HEAD --` | `reset` **만** (뒤 `HEAD` `--` 는 **별도 인자**로 깨짐) | **오류** 또는 **의도와 다름** |

```bash
# X — 쉘이 공백에서 끊음
git config --global alias.unstage reset HEAD --

# O — 한 문자열로 저장
git config --global alias.unstage "reset HEAD --"
```

→ Git 은 alias 값을 **문자열**로 저장 · 실행할 때 **`git` + 그 문자열 + 내가 친 인자** (`file`) 로 확장 (`2-17` `alias.st`).

## 유형 4. 순서·로직 빈칸

> **알고리즘·워크플로 순서** (공지: coding algorithms)

---

### 4-1 (안전한 push 순서)
**상황:** 원격 URL 을 **연결한 뒤** · 작업 저장(commit) · **남의 변경 pull** · 내 변경 **push** 하는 **일상 워크플로** (PDF Good practice).

**문제:** 아래에 **번호** (1~5).

```
( ) git push origin master
( ) git remote add origin <URL>
( ) git pull origin master
( ) git commit -m "my work"
( ) git add .
```

**정답:** 1.remote add · 2.add . · 3.commit · 4.pull · 5.push

**해설 — `5-1` `4-4` 와 다른가? (둘 다 맞음 · 상황이 다름)**

| | **`5-1` `history 6.sh` · `4-4`** | **이 문제 `5-3` `4-1`** |
|--|-----------------------------------|-------------------------|
| 상황 | 로컬 **처음** 만든 repo → **빈** GitHub | 원격 **연결 후** · 팀과 **같이** 쓰는 repo |
| 순서 | init → add → commit → branch -M → **remote add** → **push** | **remote add** → add → commit → **pull** → **push** |
| **pull** | **없음** (원격에 commit **없음**) | **있음** (남의 변경 **먼저** 받기) |
| **remote add** 위치 | commit **뒤** · push **직전** | **맨 앞** (pull 도 하니까 **먼저** 연결) |

**공통:** `remote add` 는 **push/pull 하기 전**이면 됨 · **위치만** 문제마다 다름.

**이 문제 핵심 — `commit → pull → push`:**

```
remote add   ← URL 연결 (pull/push 가능하게)
add → commit ← 내 작업 저장
pull         ← 원격 변경 **먼저** 받기 (충돌 줄이기)
push         ← 그다음 올리기
```

→ `5-1` 은 **첫 업로드** · `5-3` 은 **이미 원격이 있는 협업** + **안전 순서** 시험.

---

### 4-2
**문제:** `git remote` / `git remote -v` / `git remote show origin` — 각각 한 줄로 차이?

**정답:**  
- **`git remote`** — 등록된 원격 **이름** 목록  
- **`git remote -v`** — 이름 + **URL** (fetch/push)  
- **`git remote show origin`** — `origin` **상세 정보** (URL, 추적 브랜치 등)

**해설:** 짧게 → `-v` → `show` 순으로 **점점 자세해짐**.

---

### 4-3 (fetch vs pull)
**문제:** (1) 원격만 가져오기: `git ______ origin`  
(2) 가져와 **현재 브랜치에 합치기** 한 번에: `git ______ origin main`  
(3) (1)만 하면 로컬 브랜치가 **자동** merge되는가? (O/X)

**정답:** (1) `fetch` (2) `pull` (3) **X**

**해설:** `pull` ≈ `fetch` + `merge`. fetch만으면 merge **별도**.
