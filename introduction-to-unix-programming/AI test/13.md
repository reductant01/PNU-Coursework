### 1-2
**문제:** GCC로 C 프로그램 만들 때 **4단계**는 **전처리 → 컴파일 → 어셈블 → 링크** 순이다. ( O / X )

**정답:** **O**

**해설:** PDF slide 3 · `history 7.sh`.

| 순서 | 단계 | 도구(강의) | gcc 옵션 (`history 7.sh`) |
|------|------|------------|---------------------------|
| **1** | **전처리** Preprocessing | cpp0 | **`gcc -E`** |
| **2** | **컴파일** Compile | cc1 | **`gcc -S`** (어셈블리) |
| **3** | **어셈블** Assemble | as | **`gcc -c`** (**.o**) |
| **4** | **링크** Linking | ld | **`gcc -o`** (실행 파일) |

**왜 `-E` `-S` `-c`? — 옵션 축약 (`history 7.sh`):**

| 옵션 | 축약 | 뜻 | 멈추는 단계 · 결과 |
|------|------|-----|-------------------|
| **`-E`** | **E**xpand | **전처리**만 (`#include`·`#define` 펼침) | **.i** 수준 텍스트 (stdout) |
| **`-S`** | **S**assembly | **어셈블리(.s)** 까지 | 컴파일 후 **기계어 전 .s 파일** |
| **`-c`** | **c**ompile | **컴파일+어셈블**까지 · **링크 X** | **.o** object file |
| **`-o`** | **o**utput | **출력 파일 이름** 지정 | **4단계 링크** 후 **실행 파일** |

**암기:** **E → S → c** = 점점 **더 뒤 단계까지** · **`-o`** = 최종 **이름** 붙이기.

```
file.c  -E→  전처리된 텍스트
        -S→  file.s (어셈블리)
        -c→  file.o (object)
        -o app→  app (실행 파일, 링크 포함)
```

**헷갈림:** **`-c`** = “compile”이지만 **링크는 안 함** = **.o에서 멈춤** (1-3) · **`-o`** 는 **단계 이름이 아니라** output **파일명** 옵션.

### 1-5
**상황 (PDF slide 4~6):** 프로그램 **`unix3`** 를 만들려고 **소스가 3개** 있다.

- **`unix3-1.c`**, **`unix3-2.c`**, **`unix3-3.c`** — 각각 다른 **.c** 파일 (폴더 a·b·c **아님**)
- **`unix3.h`** — 위 `.c`들이 `#include`로 **같이 쓰는 선언** (결과물 **아님**)

**문제:** 위처럼 **`.c` 여러 개**를 각각 **`.o`** 로 만든 뒤 **링크**하면 **실행 파일 `unix3` 하나**가 된다. ( O / X )

**정답:** **O**

**해설:**

```
unix3-1.c  ──gcc -c──→  unix3-1.o  ─┐
unix3-2.c  ──gcc -c──→  unix3-2.o  ─┼── 링크 ──→  unix3  (실행 파일 1개)
unix3-3.c  ──gcc -c──→  unix3-3.o  ─┘

unix3.h  →  .o로 안 만듦 · 각 .c 안에 #include로 붙는 “공유 헤더”
```

**자주 하는 오해 (X):**

| 착각 | 실제 |
|------|------|
| `unix3` **안에** a·b·c 파일을 **불러온다** | **소스 파일 이름**이 `unix3-1.c` … 인 것뿐 |
| 여러 `.c`를 **`.h` 하나로** 만든다 | **`.h`는 처음부터 있는 선언 파일** · 최종은 **실행 파일 `unix3`** |
| `.c`마다 **실행 파일 하나씩** | **`.o` 여러 개 → 링크 → 실행 파일 1개** |

**`.c` vs `.h`:** `.c` = 코드(구현) → **`.o`** · `.h` = 선언만 → **include** (1-3·1-2 전처리).

### 1-6
**문제:** **Makefile** 레시피(명령) 줄은 **반드시 TAB** 으로 시작해야 한다. **스페이스 4칸** 으로도 된다. ( O / X )

**정답:** **X**

**해설:** PDF slide 7.

**Makefile 구조 (PDF):**

```makefile
morning: morning.c          ← target : dependency (콜론 앞·뒤)
→TAB→ gcc -o morning morning.c   ← 레시피(명령) — **TAB 필수**
```

| 부분 | 뜻 |
|------|-----|
| **`morning:`** | **target**(만들 목표) |
| **`morning.c`** | **dependency**(필요한 파일) |
| **다음 줄 명령** | **레시피** — `make`가 실행할 **shell 명령** |

**이 문제 X인 이유 — TAB vs 스페이스:**

| 들여쓰기 | `make` 동작 |
|----------|-------------|
| **TAB** (↹) | **정상** — 레시피로 인식 |
| **스페이스 4칸** | **오류** — `missing separator` 등 (5-1) |

→ Makefile은 **보기엔 똑같아도** TAB과 스페이스를 **다르게** 봄 · **명령 줄은 반드시 TAB**.

**비유:** Python 들여쓰기처럼 **문법 규칙** — 에디터에서 **Tab 키**로 넣어야 함.

### 1-7
**상황 (PDF slide 2·7):**

```makefile
morning: morning.c
	gcc -o morning morning.c
```

**문제:** Makefile **규칙**은 **`만들 것(target)` : `필요한 파일(dependency) …`** 형식이다. ( O / X )

**정답:** **O**

**해설:** PDF slide 7.

**한 줄로 읽기:**

```
morning : morning.c
  ↑         ↑
 target   dependency (의존 파일)
```

| 부분 | 뜻 | 이 예 |
|------|-----|-------|
| **target** (`:` 앞) | **make가 만들 목표** | **`morning`** (실행 파일) |
| **dependency** (`:` 뒤, 공백 구분) | **이 target에 필요한 파일** | **`morning.c`** |

**의도 (시험):** Makefile **한 줄 규칙** 문법 — **“A를 만들려면 B가 필요하다”** 를 적는 형식.

**자주 하는 오해 (X):**

| 착각 | 실제 |
|------|------|
| `:` 뒤 **아무 단어**를 자동으로 **.c로 인식** | **적어 둔 이름 그대로** 파일 (`.c`·`.h`·`.o` 다 가능) |
| make가 **알아서** 소스 찾음 | **작성자가 dependency를 직접 나열** |
| dependency는 **항상 .c** | 예: `main.o: main.c add.h` — **.c와 .h 둘 다** 가능 (`MakeFileTest2`) |

**make가 하는 일 (1-9):** `morning.c`가 `morning`보다 **새로우면** → TAB 아래 **gcc** 실행.

### 1-8
**상황 (`MakeFileTest3`):** Makefile **맨 위**에 자주 쓰는 **이름(매크로)** 을 적어 두고, 아래에서 **`$(이름)`** 으로 **반복해서** 씀.

```makefile
CC = gcc
CFLAGS = -Wall -I include
TARGET = app
...
	$(CC) $(CFLAGS) $^ -o $@
```

**문제:** **`CC`**=컴파일러 · **`TARGET`**=만들 실행 파일 · **`CFLAGS`**=컴파일 옵션 — 이런 **매크로 변수**를 Makefile에 쓸 수 있다. ( O / X )

**정답:** **O**

**해설:** PDF slide 7 (Macro: CC, TARGET, CFLAG) · `MakeFileTest3`.

| 매크로 | 뜻 | 이 예에서 |
|--------|-----|-----------|
| **`CC`** | **C** **C**ompiler — **컴파일러** | `gcc` |
| **`CFLAGS`** | **C**ompiler **FLAGS** — **컴파일러(gcc)에 넘기는 옵션 묶음** | `-Wall -I include` |
| **`TARGET`** | 최종 **만들 파일** 이름 | `app` |

**의도:** `gcc`·`-Wall`을 **여러 줄에 복붙** 안 하려고 **한 번 정의 → `$(CC)` 로 치환**.

**`$(CC)`** = “위에서 정한 **CC 값**으로 바꿔 넣기” (1-7 **규칙**과 별개 — **변수**).

### 1-9
**상황 (PDF `morning` 예):**

```makefile
morning: morning.c
	gcc -o morning morning.c
```

`morning` 실행 파일 **이미 있음** · `morning.c`만 **방금 수정**함.

**문제:** `make` 는 **의존 파일(`morning.c`)이 target(`morning`)보다 새로우면** (또는 target이 **없으면**) TAB 아래 **레시피(gcc …)** 를 실행한다. ( O / X )

**정답:** **O**

**해설:** PDF slide 2·7.

**make 판단 (시간 비교):**

| 상태 | `make` 동작 |
|------|-------------|
| **`morning.c`가 더 새김** (또는 `morning` 없음) | **gcc 실행** — 다시 빌드 |
| **`morning`이 더 새김** · `.c` 안 바뀜 | **“up to date”** — **명령 안 함** |

```
morning.c 수정됨 (14:00)  >  morning (13:00)  →  make  →  gcc 실행
morning.c 그대로 (13:00)  <  morning (14:00)  →  make  →  스킵
```

**의도:** make = **“바뀐 파일만 다시 컴파일”** (1-5와 연결) · **수동으로 gcc 칠 때마다 전체 빌드** 안 해도 됨.

**헷갈림:** “**target이 더 새우면** 빌드” (X) → **의존 파일이 더 새우면** (O).

### 1-10
**상황 (`MakeFileTest2`):** 레시피 안에서 target·dependency 이름을 **매번 손으로 쓰지 않고** **`$`로 시작하는 자동 변수**를 씀.

```makefile
app: main.o add.o
	$(CC) $(CFLAGS) $^ -o $@

%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@
```

**문제:** **`$@`**=target 이름 · **`$^`**=모든 dependency · **`$<`**=첫 번째 dependency — 이렇게 쓴다. ( O / X )

**정답:** **O**

**해설:** `history 8.sh` · `MakeFileTest2/Makefile copy 2`.

**시험에 나오는 3개 (암기):**

| 변수 | 뜻 | `app: main.o add.o` / `make main.o` 예 |
|------|-----|----------------------------------------|
| **`$@`** | **target** 이름 | `app` / `main.o` |
| **`$^`** | **모든** dependency | `main.o add.o` |
| **`$<`** | **첫 번째** dependency | `main.c` (패턴 규칙 `%.o: %.c`) |

**그 밖에 있는 Make 자동 변수 (참고):**

| 변수 | 뜻 | 비고 |
|------|-----|------|
| **`$?`** | target보다 **새로운** dependency만 | 증분 빌드에 쓰임 · **쉘 `$?`(exit status)와 다름** (12.md) |
| **`$*`** | 패턴 규칙 **`%` 자리(stem)** | `%.o: %.c` + target `add.o` → **`add`** |
| **`$+`** | 모든 dependency (**중복 포함**) | `$^`는 중복 제거 |
| **`$%`** | archive(`.a`) **멤버 이름** | `history 9.sh` 수준 — 빈도 낮음 |

**의도:** `main.o add.o`를 **규칙마다 복붙** 안 하려고 · 링크 줄은 **`$^ -o $@`**, 컴파일 줄은 **`-c $< -o $@`** 패턴이 반복됨 (`MakeFileTest3`).

### 1-11
**상황 (`MakeFileTest3`):** Makefile **위쪽 매크로** (1-8) + **규칙** 일부.

```makefile
SRC = src/main.c src/add.c
OBJ = $(SRC:.c=.o)          # → src/main.o src/add.o
DEP = $(SRC:.c=.d)          # → src/main.d src/add.d (.h 의존 기록, -MMD)
TARGET = app                # → 실행 파일 이름

all: $(TARGET)              # ① Makefile 첫 target
$(TARGET): $(OBJ)
	$(CC) $(CFLAGS) $^ -o $@
clean:
	rm -f $(TARGET) $(OBJ) $(DEP)   # app + .o + .d 삭제
.PHONY: all clean
```

| 매크로 | 뜻 | 이 예에서 |
|--------|-----|-----------|
| **`$(TARGET)`** | 최종 **실행 파일** | `app` |
| **`$(OBJ)`** | **오브젝트** (`.o`) 목록 | `src/main.o src/add.o` |
| **`$(DEP)`** | **의존 정보** (`.d`) | `src/main.d src/add.d` |

**문제:** **`.PHONY: clean`** 은 **`clean`이라는 실제 파일이 없어도** (또는 **같은 이름 파일이 있어도**) `make clean` 할 때 **항상** `rm …` 을 실행하게 한다. ( O / X )

**정답:** **O**

**해설:** `MakeFileTest3` · `MakeFileTest2`.

---

**왜 `make all` 안 치고 `make` 만 쳐도 `all` 이 도나?**

make 규칙: **target을 안 적으면 Makefile의 첫 번째 target** 을 만든다 (= **default goal**).

```
make  ≡  make all     (이 Makefile에서 첫 target이 all 이라서)
make clean            (이름을 적으면 그 target만)
```

`all` 을 **맨 위**에 두는 이유가 “**그냥 make 치면 전체 빌드**” 하려고 · PHONY와는 **별개** (PHONY = 파일로 안 본다는 선언).

---

**`.PHONY: all clean`**

일반 규칙(`target: dep`) **아님** → **`all`·`clean` 둘 다** “디스크 파일이 아닌 target” 선언.

| 명령 | 동작 |
|------|------|
| **`make`** | `all` → **`app` 빌드** (`all` 파일 안 생김) |
| **`make clean`** | `rm`으로 **`app` + `.o` + `.d` 삭제** |

**PHONY가 막는 것** (1-9): 폴더에 `all`/`clean` **이름 파일**이 있으면 make가 “최신”이라 **레시피 스킵** → PHONY 있으면 **요청 시 항상 실행**.

### 1-12

```makefile
CFLAGS = -Wall -I include

```

**문제:** **`gcc -Wall`** 은 **경고(warning) 메시지**를 출력한다. ( O / X )

**정답:** **O**

**해설:** `history 8.sh` · `MakeFileTest3`.

| | 내용 |
|--|------|
| **축약** | **`-W`**arning **all** — 흔한 **경고** 종류를 **많이** 켬 |

**의도:** `-Wall` 없이 컴파일하면 **조용히 넘어가는 실수**를 빌드할 때 잡으려고 · Makefile에 넣으면 **매번** 적용 (1-8 `CFLAGS`).

**강의 코드:** `MakeFileTest2`·`MakeFileTest3` 의 `CFLAGS`에는 **`-Wall`만** (＋`-I`·`-MMD`) · **`-g`는 없음** — 일상 빌드용.

### 1-13
**상황 (`history 9.sh`):** `./test` 로 그냥 실행하면 **어디서·왜** 틀렸는지 보기 어려움 → **gdb**로 **한 줄씩** 멈춰 가며 확인.


**문제:** **`gcc -g`** 는 **디버그(debug)** 정보를 넣어 **gdb** 에 쓴다. ( O / X )

**정답:** **O**

**해설:** `history 8.sh` · `history 9.sh`.

**`gdb` 란?**

| | 내용 |
|--|------|
| **축약** | **G**NU **D**e**b**ugger — 리눅스에서 쓰는 **C/C++ 디버거 프로그램** |
| **하는 일** | 실행 중인 프로그램을 **멈추고** · **어느 줄**인지 · **변수 값**이 뭔지 **조사** |
| **`./test` 와 차이** | 그냥 실행 = 끝까지 돌아감 · gdb = **`break` 지점에서 멈춤** → 원인 추적 |

**`-g` 와 gdb 관계**

| | 내용 |
|--|------|
| **`gcc -g`** | 빌드할 때 **소스 줄 번호·변수 이름** 등을 실행 파일에 **넣어 둠** |
| **gdb** | 그 정보를 읽어 **`main.c:10` 같은 줄** · 변수 이름으로 보여 줌 |
| **`-g` 없으면** | gdb가 **어셈블리만** 보이거나 줄·변수 추적 **거의 불가** |

**`-Wall` vs `-g` (1-12와 비교)**

| | **`-Wall`** | **`-g`** |
|--|-------------|----------|
| **목적** | 컴파일 **할 때** 경고 많이 보기 | **나중 gdb**용 디버그 정보 넣기 |
| **언제 효과** | **빌드 중** 터미널에 warning | **gdb 실행할 때** 줄·변수 보기 |
| **실행 파일** | 크기 거의 비슷 | **조금 커짐** (디버그 심볼) |
| **강의에서** | `MakeFileTest3` `CFLAGS` | `history 9.sh` gdb 예제만 |

**함께 써도 됨** — 서로 **다른 일**이라 **충돌 없음**:

```bash
gcc -Wall -g test.c -o test    # 경고도 보고 + gdb도 가능
# Makefile이면: CFLAGS = -Wall -g -I include
```

**강의가 나눈 이유:** Makefile = **매일 빌드** → **`-Wall`** 만 넣음 · gdb 연습 = **그때만** `gcc -g` 로 따로 빌드 (`history 9.sh`). 디버깅할 땐 **둘 다** 넣어도 됨.

**흐름 (gdb):** `gcc -g` 로 빌드 → `gdb ./프로그램` → `break` / `run`.

| | 내용 |

### 3-4 (history 9 · 정적 라이브러리)
**상황:** `add.o`를 **라이브러리로 포장**한 뒤 `main.o`와 **링크** (`history 9.sh`).

```bash

ar rcs libadd.a add.o           # ② 정적 라이브러리 생성
gcc main.o -L. -ladd -o app     # ③ main + libadd 링크 → app
```

**문제:** (1) **2번째 줄** 역할? (2) **`-ladd`** 가 찾는 파일?

**정답:** (1) **`libadd.a` 정적 라이브러리 생성** (2) **`libadd.a`** (`lib` + 이름 + `.a`)

**해설:** 1-14 · `history 9.sh`.

**②번째 줄 분해 (`ar rcs libadd.a add.o`)**

```bash
ar   rcs   libadd.a   add.o
│    │     │          └── 넣을 오브젝트
│    │     └── 만들 파일 (정적 라이브러리)
│    └── r=넣기  c=없으면 생성  s=인덱스
└── archiver
```

→ **`add.o`를 `libadd.a` 안에 넣어 둠** (1-14).

**③번째 줄 · `-L.` · `-ladd` (헷갈리기 쉬움)**

```bash
gcc main.o -L. -ladd -o app
```

**`-ladd` 는 `ladd` 라는 코드가 아님** — **두 덩어리**가 붙어 있음:

```
-ladd  =  -l  +  add
         │      └── 라이브러리 **이름** (우리가 만든 libadd.a 의 가운데 부분)
         └── gcc **옵션** (소문자 L) = **l**ink **l**ibrary
```

`-l add` (띄어 써도) **같음** · `l`로 끝나는 아무 단어를 찾는 게 **아님**.

| 옵션 | 뜻 |
|------|-----|
| **`-L.`** | **대문자 L** — 라이브러리 **폴더** · **`.`** = 현재 디렉터리 |
| **`-l`** | **소문자 l** — 라이브러리 **링크** (`history 7.sh`) |
| **`-l` 뒤 이름 `add`** | 파일명 **`lib` + `add` + `.a`** 를 찾음 → **`libadd.a`** |

**링커 이름 규칙 (gcc 관례):**

```
-l 뒤에 적은 이름:  add
실제 찾는 파일:     lib  +  add  +  .a   →   libadd.a
```

| `-l` 뒤 | 찾는 파일 |
|---------|-----------|
| **`add`** | **`libadd.a`** |
| **`m`** (수학) | **`libm.so`** / `libm.a` |
| **`pthread`** | **`libpthread.so`** |

**동작 순서:**

```
1. -L.     →  현재 폴더에서 라이브러리 검색
2. -l add  →  libadd.a (또는 libadd.so) 찾기
3. ②번 줄에서 만든 libadd.a 가 여기 있음  →  main.o 와 링크  →  app
```

**암기:** **`-l` = 옵션** · **`add` = 이름** · **`libadd.a` = 파일 전체 이름** (1-14에서 `ar`로 만든 것).

**전체 흐름:** `add.c`→`add.o` → `ar`로 **`libadd.a`** → `main.o`＋**`-L.`**＋**`-ladd`** → **`app`**

**이 문제는 “`.c` 여러 개 → 실행 파일 1개” 순서** · **3-4의 `-L`·`-l` (외부 라이브러리) 과는 별개**.

| 순서 | 명령 (개념) | 결과 |
|------|-------------|------|
| ① | `gcc -c unix3-1.c` (각 `.c`마다) | **`.o`** 3개 |
| ② | `gcc unix3-1.o unix3-2.o unix3-3.o -o unix3` | **실행 파일 `unix3`** |

**문제:** 위 ①·② 빈칸?

| 순서 | 작업 |
|------|------|
| ① | 각 `.c` → **`gcc -c`** → ______ |
| ② | 모든 **`.o`** → **링크** (`-o unix3`) → ______ |

**정답:** **`.o` (object file)** / **실행 파일 `unix3`**

**해설:**

```
① gcc -c   전처리+컴파일+어셈블까지만 · .h는 이때 #include로 .c에 붙음
② 링크     .o들을 합쳐 실행 파일 1개 · .h는 ②에 안 넣음 (이미 ①에 반영됨)
```

**옵션 정리 (헷갈림 방지):**

| 옵션 | 이 문제(4-2) | 3-4 (라이브러리) |
|------|--------------|------------------|
| **`-c`** | **`.o`만** 만들 때 (①) | `gcc -c add.c` |
| **`-o 이름`** | 실행 파일 **이름** 지정 (②) | `-o app` |
| **`-L.`** | **안 씀** | 라이브러리 **폴더** (`.`=현재) |
| **`-ladd`** | **안 씀** | **`libadd.a` 링크** (`-l`+`add`) |

**`-l`은 “링크 단계” 이름이 아님** → **이미 만든 라이브러리 파일**(`libxxx.a`)을 실행 파일에 **붙이라**는 옵션.

**한 줄:** ① **`-c`** = `.o` · ② **링크** = `.o` 합치기 · **`-o`** = 결과 **이름** · **`-L`/`-l`** = **라이브러리** 있을 때만 (3-4).

**`add` / `-add` / `-ladd` 차이 (3-4 연결):**

| 명령에 있는 것 | 역할 |
|----------------|------|
| **`add.o`** | **입력 파일** — 링크에 넣는 **오브젝트** (4-2 ②에서 `.o` 나열하는 것과 같음) |
| **`add`만** (`gcc … add …`) | **파일 이름**으로 취급 · `add.c`·`add` 파일을 찾음 · **라이브러리 옵션 아님** |
| **`-add`** | gcc **표준 옵션 아님** (잘못된 플래그 → 에러 가능) |
| **`-ladd`** | **`-l` + `add`** — **`libadd.a`** 를 찾아 링크 (3-4) |

→ **`add`만으로는 `libadd.a`를 안 찾음** · **`-l`이 붙어야** “라이브러리 이름 `add`” 의미.

```bash
rm  -f  app  src/main.o src/add.o  src/main.d src/add.d

│   │   │         │                      └── DEP — 의존 정보 (.h 기록, 2-11)
```

| 지우는 대상 | 매크로 | 파일 |
|-------------|--------|------|

| **오브젝트** | `$(OBJ)` | `src/main.o` `src/add.o` |

### 6-4
**상황 (`MakeFileTest3`):** Makefile **맨 위**에 소스·오브젝트 목록을 **매크로**로 적어 둠 (1-8).

```makefile
SRC = src/main.c src/add.c
OBJ = $(SRC:.c=.o)
DEP = $(SRC:.c=.d)
```

**`$(SRC:.c=.o)` 뜻:** `SRC` 각 단어에서 **`.c` → `.o` 로 바꿔 치환** (make 변수 확장).

```
SRC:  src/main.c   src/add.c
        ↓ .c→.o      ↓ .c→.o
```

| | 내용 |
|--|------|
| **하는 일** | `.c` 목록을 **`.o` 목록**으로 **자동 변환** (손으로 일일이 안 적음) |
| **`$(OBJ)` 용도** | `$(TARGET): $(OBJ)` — 링크할 **`.o` 파일들** (3-2) |
| **비슷한 것** | `$(SRC:.c=.d)` → `src/main.d src/add.d` (`DEP`, 1-11) |

**헷갈림:** shell 명령 **아님** · Makefile **변수 치환** · `gcc` 옵션 **아님**.

### 6-6
**상황:** `gcc -O2 file.c` (`history 8.sh`).

**문제:** **`-O2`** 뜻?

**정답:** **O**ptimization **level 2** — **실행 속도 최적화** (강의: “2단계”)

**해설:** `history 8.sh` · **4-1과 무관**.

| | **4-1 (빌드 4단계)** | **`-O2` (최적화 레벨)** |
|--|----------------------|-------------------------|
| **뭐냐** | 전처리→컴파일→어셈블→**링크** **순서** | 코드를 **얼마나 빠르게** 돌릴지 **옵션** |
| **숫자** | ①②③④ **단계 번호** | **O0 O1 O2 O3** — 최적화 **강도** |
| **예** | `gcc -E` `-S` `-c` | `gcc -O0` (최적화 거의 없음) · **`-O2`** (중간) · `-O3` (더 강함) |

**`-O2`의 “2”** = **최적화 2단계(레벨 2)** · **어셈블 단계(4-1 ③)** 를 말하는 게 **아님**.

**`-O0` · `-O2` · `-O3` (`history 8.sh`):**

| 옵션 | 뜻 |
|------|-----|
| **`-O0`** | **O**ptimization **0** — 최적화 **거의 안 함** (디버깅에 유리) |
| **`-O2`** | 최적화 **레벨 2** — 실행 **속도** 중간 정도로 최적화 |
| **`-O3`** | 최적화 **레벨 3** — **더 강한** 속도 최적화 |

**한 줄:** `-Ox` = **빌드 4단계 이름이 아니라** “실행 **빠르게**” **강도** 선택.

```

```

| 순서 | 단계 이름 | gcc | 하는 일 | 결과 |
|------|-----------|-----|---------|------|
| **①** | **전처리** | **`-E`** | `#include`·`#define` 펼침 | 텍스트 |
| **②** | **컴파일** | **`-S`** | **C → 어셈블리 언어** | **`.s`** |
| **③** | **어셈블** | **`-c`** | **어셈블리 → 기계어** | **`.o`** |
| **④** | **링크** | **`-o`** | `.o` 합쳐 실행 파일 | **`app`** |

**이름 헷갈림 정리:**

| 착각 | 실제 |
|------|------|
| 전처리 다음 단계 이름이 **“어셈블”** | **② 이름은 “컴파일”** — 여기서 **`.s`(어셈블리)가 생김** |
| **“어셈블”** = `.s` 만드는 단계 | **③ 어셈블** = `.s` → **`.o`** (기계어로 **조립**) |
| **`-S`** = 어셈블 단계 | **`-S`** = **② 컴파일** (assembly **파일** 출력) · **`-c`** = **③** |

**암기:** **②=어셈블리 만들기** · **③=기계어(.o)로 조립** · **`-Ox`**(O0/O2/O3)는 4단계와 **별개** (6-6).

**`TARGET` · `OBJ` · `DEP` 차이 (`MakeFileTest3`):**

| 매크로 | 파일 종류 | 예 | 역할 |
|--------|-----------|-----|------|
| **`TARGET`** | **실행 파일** | `app` | `make` 최종 결과 · `./app` 실행 |
| **`OBJ`** | **오브젝트** `.o` | `src/main.o` | 컴파일 결과 · **링크 재료** |
| **`DEP`** | **의존 기록** `.d` | `src/main.d` | `.h` 의존 저장 · make 재빌드 판단 (2-11) |
