### 1-1
**문제:** SVN은 **중앙집중형**, Git은 **분산형** 저장소 모델이다. ( O / X )

**정답:** **O**

**해설 — 왜 중앙집중 vs 분산?**

**중앙집중형(SVN):** **서버 한 곳**만이 “진짜” 저장소(전체 히스토리·모든 파일).

```
[개발자 PC]  ──checkout/update──▶  [SVN 서버]  ◀──commit──  [다른 PC]
   (작업 복사본만)                  (유일한 저장소)
```

→ commit·log 조회는 **서버 연결**이 필요한 경우가 많음 · 서버 없으면 **공식 기록**에 접근 어려움.

**분산형(Git):** **각 PC의 `.git`** 이 **저장소 전체**(커밋 히스토리 포함)를 가짐.

```
[내 PC .git]  ◀──push/pull──▶  [GitHub 등 원격]  ◀──▶  [팀원 PC .git]
  (완전한 복사본)                  (공유용 복사본)        (완전한 복사본)
```

→ **오프라인**에서도 `commit`·`log`·`branch` 가능 · 원격은 **동기화(공유)** 용 · `push`/`pull`로 맞춤.

| | **SVN (중앙)** | **Git (분산)** |
|--|----------------|----------------|
| “진짜” 저장소 | **서버 1곳** | **각자 `.git`** |
| PC에 있는 것 | 주로 **작업 파일** | **히스토리까지 포함** |
| 서버 없을 때 | 공유 기록 **어려움** | 로컬에서 **계속 작업** |

→ 문제 문장 그대로 **O**.

### 1-5
**문제:** `git diff`는 **add 전** 작업 폴더 변경, `git diff --cached`는 **add 후** 스테이징 변경을 본다. ( O / X )

**정답:** **O**

**해설 — `add`가 뭐야?**

Git은 파일이 **세 군데**를 거침:

```
[작업 폴더]  ──git add──▶  [스테이징]  ──git commit──▶  [.git 저장소]
  (지금 수정 중)            (커밋 예정)                  (영구 기록)
```

**`git add`** = “이 변경을 **다음 commit에 넣을 목록(스테이징)** 에 올려 둬”.

| 단계 | 파일 상태 |
|------|-----------|
| 파일 수정만 함 | **작업 폴더**에만 변경 |
| **`git add 파일`** 후 | **스테이징**에도 올라감 (commit 대기) |
| **`git commit`** 후 | **저장소**에 스냅샷 저장 |

**`diff` 두 종류:**

| 명령 | 비교 대상 | 언제 쓰나 |
|------|-----------|-----------|
| **`git diff`** | **작업 폴더** vs 마지막 commit | **`add` 전** · 아직 스테이징 안 한 수정 (`6-1`) |
| **`git diff --cached`** | **스테이징** vs 마지막 commit | **`add` 후** · commit 전에 “뭐 넣을지” 확인 (`6-2`) |

**예:** `rea.txt` 수정

| 상태 | `git diff` | `git diff --cached` |
|------|------------|---------------------|
| 수정만 · **add 안 함** | **있음** | 없음 |
| **`git add rea.txt` 후** | 없음 | **있음** |

→ 문제 문장 그대로 **O**.

### 1-6
**문제:** `git reset HEAD -- file`은 **unstage**(스테이징 취소), `git checkout -- file`은 **작업 폴더 수정 폐기**다. ( O / X )

**정답:** **O**

**해설 — `HEAD`가 뭐야?**

**`HEAD`** = “**지금 내가 서 있는 commit**” 을 가리키는 **포인터** (보통 **가장 최근 commit**).

```
… ← [이전 commit] ← [HEAD = 마지막 commit] ← (아직 안 한 add/commit)
```

**두 명령 비교** (`rea.txt` 를 수정하고 `git add` 한 뒤):

| 명령 | 하는 일 | 작업 폴더 파일 | 스테이징 |
|------|---------|----------------|----------|
| **`git reset HEAD -- rea.txt`** | **unstage** (스테이징에서 **내림**) | **그대로** (수정 유지) | add **취소** |
| **`git checkout -- rea.txt`** | 작업 폴더 수정 **폐기** | **HEAD(마지막 commit) 내용**으로 복원 | 영향 없음 |

**`reset HEAD` 에서 HEAD:** 스테이징을 **“HEAD가 가리키는 commit 상태”** 로 맞춤 → **올려 둔 것만 취소**.

**`checkout --` 에서 HEAD:** 작업 폴더 파일을 **HEAD commit 버전**으로 되돌림 → **수정 내용 사라짐**(주의).

→ 문제 문장 그대로 **O**.

### 1-7 (`git status -s` · 두 열)
**상황:** `git status` = 저장소 **상태 확인** · **`-s`** = **short** (한 줄 요약).

앞 **2칸** = `[1열: 스테이징] [2열: 작업 폴더]` + 파일이름

**경우 1** — `rea.txt` 수정만 · **`git add` 안 함**:

```bash
git status -s
#  M rea.txt
```

**경우 2** — 수정 후 **`git add rea.txt`** · commit 전:

```bash
git status -s
# M  rea.txt
```

**문제:** 위처럼 **1열 `M`** = staged(스테이징) · **2열 `M`** = working tree만 수정(아직 add 안 함) 이라고 볼 수 있다. ( O / X )

**정답:** **O**

**해설:**

| 열 | 보는 곳 | `M` 의미 |
|----|---------|----------|
| **1열** | **스테이징** | `add` 한 변경 (`M  rea.txt`) |
| **2열** | **작업 폴더** | 수정만 · add **안 함** (` M rea.txt`) |

→ `5-1` · `5-2` · `6-7` 표와 같음.

### 1-10 (clone · 저장소 복사)
**상황:**

```bash
git clone https://github.com/user/project.git   # 원격 → 내 PC
cd project
```

**문제:** `clone` 하면 **저장소 전체 + commit 히스토리**가 **로컬(내 PC)** 에 복사된다. ( O / X )

**정답:** **O**

**해설:**

**로컬(local)** = **내 컴퓨터** 안의 폴더 · `.git` 포함.

| | **가져오는 것** |
|--|----------------|
| **`git clone`** | 파일 + **`.git`(전체 히스토리)** → **로컬에 완전한 저장소** |
| SVN checkout | 주로 **작업 파일** · 히스토리는 **서버** 쪽 |

→ **`1-1` 과 연결:** 로컬에 `.git` 이 있으니 **인터넷 없이** `git log` · `git commit` · `git branch` 가능 · `push`/`pull` 은 **동기화**할 때만.

(`checkout` 단독 = 이미 있는 저장소에서 **브랜치 이동** · `clone` 이 “처음 통째로 가져오기”)

### 1-11 (commit · 스냅샷)
**상황:** `rea.txt` · `main.c` 두 파일이 있는 프로젝트.

```bash
git add .
git commit -m "first version"    # -m = commit 메시지를 여기 적음
```

**문제:** Git은 commit 할 때 **그 순간 프로젝트 상태 전체**를 **스냅샷(snapshot)** 으로 저장한다. ( O / X )

**정답:** **O**

**해설:**

**`-m`** = **message** · commit **설명**을 **명령줄에서** 바로 적음 (`2-6`).

| | |
|--|--|
| **`git commit -m "first version"`** | 메시지 **한 줄**로 commit |
| **`git commit` 만** | 편집기(vi 등) 열려서 메시지 **직접 입력** |

→ `"first version"` = “이 commit 이 **무슨 변경인지**” 나중에 `git log` 에 남는 메모.

**스냅샷** = 그 시점 **사진 한 장** (commit 시점의 **파일 모습** 기록).

| 저장 방식 | 비유 |
|-----------|------|
| **스냅샷 (Git)** | “**지금** 폴더 상태 **통째로** 저장” |
| **diff만 (일부 VCS)** | “**바뀐 줄만** 메모” |

**예:** commit 1에 `rea.txt`·`main.c` 둘 다 있음 → 그 commit = **두 파일이 그때 어떻게 생겼는지** 묶음.

→ `git diff` 는 **스냅샷끼리 비교**해서 차이를 **보여 주는** 명령 (`1-5`) · Git **저장 단위**는 스냅샷 개념 (PDF).

### 2-15
**상황:** 브랜치 이름을 `main`으로 **강제** 변경 (`history 6.sh`).

```bash

```

**정답:** `-M`

**해설:** 둘 다 브랜치 **이름 바꾸기(move)** · **출력 형식 차이가 아니라** “이미 있는 이름”일 때 **동작**이 다름.

| | 의미 | `main` 브랜치가 **이미 있을 때** |
|--|------|----------------------------------|
| **`-m`** (move) | 현재 브랜치 **이름 변경** | **실패** (에러 · 이름 충돌) |
| **`-M`** (move **force**) | **강제** 이름 변경 | **덮어써서** 변경 (**성공**) |

```bash
git branch -m main    # master → main (main 없을 때 OK)
git branch -M main    # main 있어도 **강제로** 현재 브랜치를 main 으로 (`history 6.sh`)
```

**`history 6.sh`:** GitHub 기본 브랜치가 `main` 이라 초기 `master` 를 **`git branch -M main`** 으로 맞춤.

→ 이 문제 빈칸 = **이미 `main` 이 있어도** 되게 하려면 **`-M`**.

### 2-16
**상황:** 첫 push 시 upstream 설정.

```bash
git push ______ origin main
```

**정답:** `-u`

**해설:**

**upstream(업스트림)** = 내 **로컬 브랜치**가 **어느 원격 브랜치와 짝**인지 정해 둔 것.

```
[내 PC main]  ←──짝(upstream)──→  [GitHub origin/main]
```

**`git push -u origin main`** = (1) GitHub에 push (2) **로컬 `main` ↔ `origin/main` 짝** 등록.

| | push 명령 |
|--|-----------|
| **첫 push** | `git push -u origin main` (짝 **설정**) |
| **이후** | `git push` 만 해도 **어디로 보낼지** 알아서 `origin main` |

→ **`-u`** = `--set-upstream` (upstream **한 번** 잡아 두기).

| 명령 | 하는 일 | 어디에 |
|------|---------|--------|
| **`git init`** | **빈 Git 저장소** 생성 (`.git` 폴더 생김) | **내 PC** |
| **`git remote add origin <URL>`** | 원격 저장소 **주소 등록** (이름 `origin`) | **내 PC `.git` 설정** |

```
git init
  → 내 폴더가 Git 프로젝트가 됨 (로컬만 · GitHub 아직 없음)

git remote add origin https://github.com/user/repo.git
  → “push/pull 할 **GitHub 주소**를 origin 이라 부르자” 만 **등록** (아직 업로드 X)
```

**이 워크플로 순서:**

| 순서 | 명령 | 의미 |
|------|------|------|
| 1 | `init` | **로컬** 저장소 만들기 |
| 2~3 | `add` · `commit` | 첫 스냅샷 **로컬**에 저장 |
| 4 | `branch -M main` | 브랜치 이름 **main** 으로 (`2-15`) |
| 5 | `remote add origin` | GitHub **주소 연결** |
| 6 | `push -u origin main` | GitHub에 **올리기** + upstream (`2-16`) |

→ **init** = 저장소 **생성** · **remote add** = 원격 **주소만 붙이기** (서로 다른 단계).

---

### 3-3

```bash

```

### 4-4 (history 6.sh · 첫 GitHub 업로드 순서)
**상황:** `history 6.sh` · **빈 폴더**에서 GitHub에 **처음** 올릴 때.

**문제:** 아래에 **번호** (1~6).

```
( ) git push -u origin main
( ) git init
( ) git add .
( ) git commit -m "first commit"
( ) git branch -M main
( ) git remote add origin <URL>
```

**정답:** 1.init · 2.add . · 3.commit · 4.branch -M main · 5.remote add · 6.push -u

**해설 — 헷갈리는 점:**

**Q: `branch -M main` 전에 `add`·`commit` 돼? 브랜치 없으면 commit 안 되지 않나?**

→ **`git init` 하면 브랜치가 이미 있음** (기본 이름 `master` 또는 `main`).

```
git init
# → .git 생성 + 현재 브랜치 master(또는 main) · "No commits yet" 상태
```

| 단계 | 명령 | 하는 일 |
|------|------|---------|
| 1 | **`init`** | 로컬 저장소 + **기본 브랜치 자동 생성** |
| 2 | **`add .`** | 스테이징 (브랜치 **이미 있음** · OK) |
| 3 | **`commit`** | 그 브랜치에 **첫 스냅샷** 저장 |
| 4 | **`branch -M main`** | 브랜치 **새로 만드는 게 아님** · `master`→`main` **이름만 변경** (`2-15`) |
| 5 | **`remote add`** | GitHub **주소 등록** (`3-2`) |
| 6 | **`push -u`** | GitHub에 **업로드** + upstream (`2-16`) |

**`branch -M main` 이 commit 뒤인 이유:** commit 은 **기본 브랜치**에서 해도 됨 · GitHub 맞추려고 push **전에** 이름을 `main` 으로 바꿈 (`3-2`).

→ **브랜치는 init 때 생김** · `-M` 은 **이름 변경** · add/commit 은 **그 전에** 가능.

---

### 4-5 (commit ID)
**상황:** `git log` 에 나오는 commit 마다 **40자리 16진수** ID가 붙음.

```
commit a1b2c3d4e5f6789...   ← 이 긴 문자열
```

**문제:** 이 **고유 ID**의 이름은? (40자 16진 · 체크섬)

**정답:** **SHA-1 hash** (또는 **SHA-1 체크섬** · **commit ID**)

**해설:**

**hash(해시)** = 내용을 **짧은 고정 길이 코드**로 바꾼 것 · **지문**처럼 **그 commit 만의 ID**.

**SHA-1** = **S**ecure **H**ash **A**lgorithm **1** (보안 해시 알고리즘 1번).

| 용어 | 뜻 |
|------|-----|
| **SHA-1** | 어떤 데이터(commit 내용)를 **40자 16진**으로 만드는 **규칙/알고리즘** 이름 |
| **hash** | 그 규칙으로 만든 **결과값** (commit ID) |
| **체크섬** | 내용이 **1글자만** 바뀌어도 ID가 **완전히** 바뀜 → **무결성 확인**용 |

→ Git은 commit마다 **SHA-1 hash** 를 ID로 씀 · `git log --oneline` 의 `1677b2d` = **앞 7자만** 짧게 본 것 (`6-4`).

### 5-1

### 5-2
**상황:** 5-1 다음 **`git add rea.txt`**, commit 전.

**문제:** `M`은 **몇 번째 열**?

**정답:** **1번째 열** (`M  rea.txt`)

### 5-3 (untracked · `??`)
**상황:** Git 저장소 안에 **`foo.txt`를 새로 만듦** · **`git add` 한 적 없음** · commit에도 **한 번도 안 들어간** 파일.

```bash
touch foo.txt          # 새 파일 생성
git status -s
```

**문제:** 출력 **한 줄**?

**정답:** `?? foo.txt`

**해설:**

**untracked** = Git이 **처음 보는 파일** (commit 기록에 **없음** · `add` **안 함**).

**`??`** = “아직 Git **관리 안 함**”

---

**`M` vs `A` — add 후 1열이 뭐냐?**

| 파일 종류 | `add` 후 1열 | 이유 |
|-----------|--------------|------|
| **예전 commit 에 있던 파일** 수정 (`rea.txt` · `5-1`→`5-2`) | **`M`** | **M**odified = **바뀐** 파일 |
| **처음 만든 새 파일** (`foo.txt` · `5-4`) | **`A`** | **A**dded = **새로 넣는** 파일 |

→ **새 파일**은 `M`이 아니라 **`A`** · `M`은 “이미 알고 있던 파일이 **변경됨**”.

**`foo.txt` 한 파일만 보면:**

| 단계 | `status -s` |
|------|-------------|
| 새로 만듦 · add 안 함 (이 문제) | `?? foo.txt` |
| `git add foo.txt` | `A  foo.txt` (`5-4`) |
| commit 후 | (깨끗 · 표시 없음) |

---

### 5-4
**상황:** `5-3`의 `foo.txt` 를 **`git add foo.txt`** 함 (새 파일 · commit 전).

**문제:** `git status -s` 1열 표기는?

**정답:** **`A`** (예: `A  foo.txt`)

**해설:** 새 파일 add = **A**dded · 기존 파일 수정 add = **M** (`5-3` 표).

### 5-5
**상황:** `git status` 출력: `Your branch is ahead of 'origin/main' by 2 commits.`

**문제:** (1) 의미 한 줄 (2) 보통 다음에 할 명령?

**정답:** (1) 로컬에 원격보다 **2 commit 앞섬** (push 안 함) (2) **`git push`**

**해설:** 이 문장은 **`git status` (일반)** 에 나옴 · **`-s` 와 역할이 다름** (`1-7`).

| 명령 | 주로 보여 주는 것 |
|------|-------------------|
| **`git status`** | 브랜치·**원격 비교**(ahead/behind) + 파일 상태 **자세히** |

| **`git status -sb`** | `-s` 파일 형식 + **브랜치·ahead/behind** (`-b` = branch) |

→ **5-5·5-6** = **`-s` 없는** `git status` 의 **원격 비교** 메시지.

### 6-3
**상황:** `README.md` 수정, **`add` 안 함**.

**문제:** 아래 중 출력 **있는** 것? (모두 고르기)

- `git diff`
- `git diff --cached`
- `git diff HEAD`

**정답:** `git diff` · `git diff HEAD` · `--cached`는 **없음**

**해설 — `diff` 세 가지 (`1-5`·`1-6`):**

**`HEAD`** = **마지막 commit** (`1-6`).

| 명령 | **뭘과 뭘** 비교? | **add 안 함** (이 문제) |
|------|-------------------|------------------------|
| **`git diff`** | **작업 폴더** vs **스테이징** (add **안 한** 부분만) | **있음** |
| **`git diff --cached`** | **스테이징** vs **HEAD(commit)** (add **한** 부분만) | **없음** (스테이징 비어 있음) |
| **`git diff HEAD`** | **(작업 폴더＋스테이징)** vs **HEAD** · commit 후 **아직 안 넣은 변경 전부** | **있음** |

```
마지막 commit (HEAD)
    ↕  git diff HEAD        ← 스테이징+작업 폴더 **합쳐서** HEAD 와 비교
    ↕  git diff --cached    ← add 한 부분만
[스테이징]
    ↕  git diff             ← add 안 한 부분만
[작업 폴더 README.md 수정]  ← 이 문제
```

→ **`diff HEAD`** = `diff` + `--cached` 를 **한꺼번에** 본 것과 같음 · **add 안 함**이면 스테이징이 비어 있어 `diff` 와 **출력 같음** (`6-1`).

### 6-4 (`git log` vs `--oneline`)
**상황:** commit이 **3개** 있는 저장소 · 둘 다 **같은 히스토리**를 보여 주되 **출력 형식**만 다름 (`history 6.sh`).

**문제:** (1) `git log` (2) `git log --oneline` — **줄 수** 차이?

**정답:** (1) commit당 **여러 줄** (2) **총 3줄** (commit 1개당 1줄)

**해설 — 뭐가 다른가?**

둘 다 **과거 commit 목록**을 보여 줌 · **`--oneline`** = **한 줄 요약**.

**`git log` (기본 · 자세히):**

```
commit a1b2c3d4e5f6... (전체 hash)
Author: name <email>
Date:   Mon Jun 8 12:00:00 2026

    third commit

commit 9f8e7d6c5b4a...
Author: ...
Date:   ...

    second commit

(... 3번째 commit 도 같은 패턴)
```

→ commit **1개** = hash + author + date + 메시지 → **여러 줄** · 3개면 **대략 10줄 이상**.

**`git log --oneline` (짧게):**

```
a1b2c3d third commit
9f8e7d6 second commit
3c2b1a0 first commit
```

→ commit **1개 = 1줄** (hash **앞 7자** + 메시지) · 3개면 **정확히 3줄**.

| | **`git log`** | **`git log --oneline`** |
|--|---------------|-------------------------|
| 목적 | **자세한** 기록 | **한눈에** 훑기 |
| commit 1개 | **여러 줄** | **1줄** |
| commit 3개 | **많은 줄** | **3줄** |
