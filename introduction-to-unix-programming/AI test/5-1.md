# Git 중간고사 연습 문제 (정답·해설 포함)

> 출처: `Lecture Notes/english/5-1-Git-How-To-USE-보안.pdf`, `history 6.sh`

**먼저 읽기 — Git을 이렇게 이해하면 됩니다**

```
[작업 폴더]  →  git add  →  [스테이징]  →  git commit  →  [저장소(.git)]
  (수정만 함)              (커밋 준비)                  (영구 저장)
```

- **작업 폴더**: 지금 편집하는 파일
- **스테이징**: `git add`로 “다음 commit에 넣을 것”을 모아 둔 곳
- **저장소 (`.git`)**: `git commit`으로 확정된 기록

**이 파일 읽는 법:** 각 문제는 **상황 → 문제(빈칸)** 까지만 보고 풀고, 그다음 **정답·해설**을 확인하세요.

## 1. 개념 (단답·OX)

### 1-1
**묻는 것:** SVN과 Git의 저장소 구조(모델) 차이

SVN은 (          ) 모델이고, Git은 (          ) 모델이다.  
→ 보기: 중앙집중형 / 분산형

**정답:** SVN — **중앙집중형**, Git — **분산형**

**해설:** SVN은 서버 한 곳만 “진짜” 저장소입니다. Git은 각자 PC에 저장소 전체를 갖고 `push`/`pull`로 맞춥니다.

---

### 1-2
**묻는 것:** Git이 커밋마다 붙이는 고유 ID 이름

Git에서 각 커밋을 식별하는 40자리 16진수 문자열의 이름은?

**정답:** **SHA-1 hash** (체크섬, 커밋 ID)

**해설:** SVN의 1, 2, 3… 대신, 커밋 내용으로 만든 고유 코드입니다. `git log --oneline`의 `1677b2d` 같은 값이 앞 7자입니다.

---

### 1-3
**묻는 것:** 로컬 Git의 세 영역 이름 (순서대로)

로컬 Git 프로젝트의 세 영역을 순서대로 쓰시오.

**정답:**  
1. Working directory  
2. Staging area  
3. Git directory (`.git`)

**해설:** 수정 → `add`(스테이징) → `commit`(저장소) 순서와 대응됩니다.

---

### 1-4
**묻는 것:** 파일을 저장소에 넣기까지 기본 3단계

Git 기본 워크플로우 3단계를 순서대로 쓰시오.

**정답:** ① 파일 수정 → ② `git add` → ③ `git commit`

**해설:** `add` 없이는 스테이징이 비어 있어 일반적으로 `commit`할 내용이 없습니다.

---

### 1-5
**묻는 것:** GitHub 없이 Git 사용 가능 여부

GitHub를 반드시 써야 Git을 사용할 수 있다. ( O / X )

**정답:** **X**

**해설:** 로컬만으로 `init` → `add` → `commit` 가능합니다. GitHub는 원격 공유용입니다.

---

### 1-6
**묻는 것:** `git status -s` 출력에서 `M`의 위치 의미

`rea.txt`를 수정한 뒤 `git status -s`를 실행했다.  
`M`이 **첫 번째 열** / **두 번째 열**이면 각각 어느 영역을 뜻하는가?

**정답:** 1열 → Staging area / 2열 → Working tree (작업 폴더만 수정)

**해설:**
```
 M rea.txt    ← 2열 M: add 안 함
M  rea.txt    ← 1열 M: add 함 (커밋 대기)
```

## 2. 명령·옵션 빈칸 채우기

> 아래는 모두 **「이런 일을 하려고 할 때, 빈칸에 뭐가 들어가야 할까?」** 형식입니다.

---

### 2-1
**상황:** 앞으로 이 PC에서 하는 **모든** Git 프로젝트에, 커밋 작성자 이름을 `"홍길동"`으로 저장하고 싶다.

**문제:** 빈칸에 들어갈 옵션은?

```bash
git config ______ user.name "홍길동"
```

**정답:** `--global`

**해설:** `--global` = 전역 설정. 한 프로젝트만이면 `--global` 없이 그 폴더에서 설정합니다.

---

### 2-2
**상황:** 전역으로 커밋에 붙일 **이메일 주소**를 설정한다.

**문제:** 빈칸에 들어갈 항목 이름은?

```bash
git config --global user.______
```

**정답:** `email`

**해설:** `user.name`과 함께 커밋 메타데이터로 저장됩니다.

---

### 2-3
**상황:** 지금 Git에 어떤 설정이 들어가 있는지 **목록**으로 확인하고 싶다.

**문제:** 빈칸에 들어갈 옵션은?

```bash
git config ______
```

**정답:** `--list`

**해설:** `history 6.sh`의 `git config --list`와 같습니다.

---

### 2-4
**상황:** 프로젝트 폴더에 들어가서, 이 폴더를 **새 Git 저장소**로 만들고 싶다. (`.git` 폴더 생성)

**문제:** 빈칸에 들어갈 하위 명령은?

```bash
git ______
```

**정답:** `init`

**해설:** `clone`은 이미 있는 저장소를 복사할 때, `init`은 빈 저장소를 만들 때 씁니다.

---

### 2-5
**상황:** 첫 커밋 전에, **현재 폴더 안의 모든 파일**을 한 번에 스테이징하고 싶다.

**문제:** `git add` 뒤 빈칸에 들어갈 인자는? (마침표의 의미도 쓰시오.)

```bash
git add ______
```

**정답:** `.` (현재 디렉터리 전체)

**해설:** PDF에서도 `git add .`의 `.`은 “this directory(이 디렉터리)”입니다.

---

### 2-6
**상황:** 스테이징된 파일을 저장소에 기록하면서, 메시지 `"Initial commit"`을 **명령줄에서 바로** 적고 싶다.

**문제:** 빈칸에 들어갈 옵션은?

```bash
git commit ______ "Initial commit"
```

**정답:** `-m`

**해설:** `-m` 없으면 vim 등 편집기가 열려 메시지를 입력합니다.

---

### 2-7
**상황:** GitHub에 있는 남의 저장소를 **내 PC로 통째로 복사**해 오고 싶다.

**문제:** 빈칸에 들어갈 하위 명령은?

```bash
git ______ https://github.com/user/repo.git
```

**정답:** `clone`

**해설:** URL의 저장소 + 히스토리를 로컬에 만듭니다.

---

### 2-8
**상황:** `rea.txt`를 수정만 했을 때 / `git add rea.txt` 한 뒤 — 각각 **어떤 diff 명령**으로 차이를 보는가?

**문제:** 빈칸을 채우시오.

| 보고 싶은 것 | 명령 |
|--------------|------|
| 아직 `add` **안 한** 변경 | `git ______` |
| `add` **한 뒤**(스테이징된) 변경 | `git diff ______` |

**정답:** `diff` / `--cached`

**해설:**  
- `git diff` → 작업 폴더 vs 스테이징
- `git diff --cached` → 스테이징 vs 마지막 커밋  

---

### 2-9
**상황:** `git add`까지 했는데, 커밋하기 **전에** 스테이징만 취소하고 싶다. (파일 수정 내용은 그대로 둠)

**문제:** 빈칸에 들어갈 기호는?

```bash
git reset HEAD ______ readme.txt
```

**정답:** `--`

**해설:** `reset HEAD -- 파일` = unstage. 수정 내용은 작업 폴더에 남습니다.

---

### 2-10
**상황:** 파일을 고쳤다가 마음이 바뀌어, **작업 폴더의 수정을 버리고** 마지막 커밋 상태로 되돌리고 싶다.

**문제:** 빈칸에 들어갈 기호는?

```bash
git checkout ______ readme.txt
```

**정답:** `--`

**해설:** `checkout -- 파일` = 로컬 수정 폐기. **되돌릴 수 없으니** 주의해서 씁니다.

---

### 2-11
**상황:** 커밋 기록을 **한 줄씩 짧게** 보고 싶다. (커밋 ID 앞 7자 + 메시지)

**문제:** 빈칸에 들어갈 옵션은?

```bash
git log ______
```

**정답:** `--oneline`

**해설:** PDF 예: `1677b2d Edited first line of readme`

---

### 2-12
**상황:** 커밋 로그 중 **가장 최근 5개만** 보고 싶다.

**문제:** 빈칸에 들어갈 옵션은?

```bash
git log ______
```

**정답:** `-5`

**해설:** 숫자는 “최근 N개” 의미입니다 (`-3`, `-10` 등).

---

### 2-13
**상황:** 원격 저장소(GitHub)의 `master` 브랜치 내용을 **가져와서** 내 현재 브랜치에 합치고 싶다.

**문제:** 빈칸을 채우시오. (`origin`, `master` 각각 무엇인지 2-15 참고)

```bash
git pull ______ ______
```

**정답:** `origin` `master`

**해설:**  
- `pull` = fetch + merge  
- `origin` = clone 시 붙는 **원격 URL 별칭**  
- `master` = 가져올 **원격 브랜치 이름** (`main`도 가능)

---

### 2-14
**상황:** 내 로컬에서 만든 커밋을 원격의 `master` 브랜치에 **올리고** 싶다.

**문제:** 빈칸을 채우시오.

```bash
git push ______ ______
```

**정답:** `origin` `master`

**해설:** `pull`은 당겨오기, `push`는 밀어올리기. 순서는 보통 **commit → pull → push** (4-1).

---

### 2-15
**상황:** 2-13, 2-14에서 쓴 `origin`과 `master`가 무엇을 가리키는지 설명하시오.

**문제:** 각각 한 줄로 쓰시오.

**정답:**  
- **origin** — `git clone`할 때 정해진 **원격 저장소 주소의 별명**  
- **master** — 그 원격에서 push/pull하는 **브랜치 이름**

**해설:** `history 6`에서는 브랜치 이름을 `main`으로 쓰기도 합니다 (`git push origin main`).

---

### 2-16 (history 6)
**상황:** 현재 브랜치 이름을 `main`으로 **바꾸려** 한다. 같은 이름의 브랜치가 이미 있어도 **강제로** 바꾸고 싶다.

**문제:** 빈칸에 들어갈 옵션은? (`-m`과 `-M` 중 강제는?)

```bash
git branch ______ main
```

**정답:** `-M`

**해설:**  
- `-m` — 이름 변경 (move), 충돌 시 실패할 수 있음  
- `-M` — **강제** 이름 변경 (move force)  

---

### 2-17 (history 6)
**상황:** 원격 `origin`을 처음 등록한 뒤, 로컬 `main` 브랜치를 push하면서 **다음부터 `git push`만 쳐도** `origin/main`으로 가게 연결하고 싶다.

**문제:** 빈칸에 들어갈 옵션은?

```bash
git remote add origin https://github.com/user/repo.git
git push ______ origin main
```

**정답:** `-u`

**해설:** `-u` = `--set-upstream`. upstream(추적 브랜치)을 설정합니다.

---

### 2-18 (history 6)
**상황:** 원격에 무엇이 올라왔는지 **정보만 먼저** 받고, 아직 내 작업 파일에 자동으로 합치지는 않고 싶다.

**문제:** 빈칸에 들어갈 하위 명령은?

```bash
git ______
```

**정답:** `fetch`

**해설:**  
- `fetch` — 원격 정보만 다운로드  
- `pull` — fetch + **merge**까지 한 번에

`rea.txt`를 편집기로 수정했다. **`git add`는 하지 않았다.**

---

#### 3-1
**문제:** `git status -s`를 실행했을 때, `M`은 **몇 번째 열**에 나오는가?

**정답:** **2번째 열**

**해설:** 스테이징 전이므로 ` M rea.txt` 형태 (2열 M).

---

#### 3-2
**문제:** `git diff` / `git diff --cached` — 각각 **출력이 있는가, 없는가?**

**정답:** `git diff` **있음** / `git diff --cached` **없음**

**해설:** 변경이 작업 폴더에만 있으므로 일반 `diff`만 보입니다.

---

### 상황 B
상황 A 다음, `git add rea.txt`를 실행했다. **아직 `commit`은 안 했다.**

---

#### 3-3
**문제:** `git status -s`에서 `M`은 **몇 번째 열**인가?

**정답:** **1번째 열**

**해설:** `add` 후이므로 `M  rea.txt` (1열 M).

---

#### 3-4
**문제:** `git diff` / `git diff --cached` — 각각 무엇을 보여 주는가? (있음/없음 + 의미)

**정답:**  
- `git diff` — **없음** (add 안 된 차이 없음)  
- `git diff --cached` — **있음** (다음 commit에 들어갈 변경)

**해설:**

| 단계 | status -s | git diff | git diff --cached |
|------|-----------|----------|-------------------|
| 수정만 | 2열 M | O | X |
| add 후 | 1열 M | X | O |

## 4. 워크플로·순서

### 4-1
**상황:** 로컬에서 작업을 마쳤고, GitHub 원격 저장소에 **안전하게** 반영하려 한다. (PDF Good practice)

**문제:** 올바른 순서 3단계를 쓰시오.

**정답:**  
1. 로컬 **add & commit**  
2. **`git pull`** (원격 변경 먼저 받기)  
3. **`git push`** (내 변경 올리기)

**해설:** push를 먼저 하면 원격과 어긋나 거절·충돌이 날 수 있습니다.

---

### 4-2
**상황:** 어떤 학생이 원격 반영 순서를 아래처럼 적었다.

① `git push` → ② `git pull` → ③ `git commit`

**문제:** 맞으면 O, 틀리면 X. 맞는 순서를 쓰시오.

**정답:** **X** — **commit → pull → push**

**해설:** commit 전에는 push할 로컬 기록이 없고, pull 전 push는 위험합니다.

---

### 4-3
**상황:** 새 기능을 `experimental` 브랜치에서 개발한 뒤, `master`에 합치려 한다.

**문제:** 아래 목적에 맞게 빈칸(명령) 4줄을 **순서대로** 쓰시오.

1. `experimental` 브랜치 **만들기**  
2. 그 브랜치로 **이동**  
3. 다시 `master`로 **이동**  
4. `experimental` 내용을 `master`에 **병합**

```bash
git ______ experimental
git ______ experimental
git ______ master
git ______ experimental
```

**정답:**
```bash
git branch experimental
git checkout experimental
git checkout master
git merge experimental
```

**해설:** `branch`는 만들기만, `checkout`은 이동, `merge`는 합치기입니다.

## 5. SVN vs Git

### 5-1
**묻는 것:** “완전한 히스토리”가 어디에 있고, Git clone/checkout은 무엇과 같은가

**문제:**  
- SVN에서 완전한 파일 히스토리를 갖는 곳은?  
- Git에서 checkout/clone은 무엇을 가져오는가?

**정답:**  
- SVN: **중앙 서버 저장소**  
- Git: **저장소 전체 + 히스토리** (로컬에 복사)

**해설:** Git은 “최신 파일만”이 아니라 repo 통째 복제에 가깝습니다.

---

### 5-2
**묻는 것:** Git이 분산형이라 로컬에서 할 수 있는 일이 많은 이유

**문제:** 한 문장으로 설명하시오.

**정답:** 각 사용자 PC에 **전체 저장소 복사본**이 있어 `log`, `commit`, `branch` 등을 **네트워크 없이** 할 수 있기 때문.

**해설:** 서버 없이도 대부분의 Git 작업이 로컬에서 끝납니다.

---

## 6. 표 완성

**상황:** PDF 명령 표 — 왼쪽 명령이 **오른쪽에서 무엇을 하는지** 맞추기

**문제:** 설명 칸을 채우시오.

| 명령 | 설명 (빈칸) |
|------|-------------|
| `git clone url [dir]` | |
| `git add files` | |
| `git commit` | |
| `git status` | |
| `git diff` | |
| `git pull` | |
| `git push` | |

---

**정답·해설**

| 명령 | 설명 | 해설 |
|------|------|------|
| `git clone` | 저장소 **복사** | URL/repo 통째로 로컬에 생성 |
| `git add` | **스테이징**에 추가 | 다음 commit 후보로 올림 |
| `git commit` | 스냅샷 **영구 저장** | `.git`에 기록 |
| `git status` | working / staging **상태 확인** | 수정·스테이징 여부 |
| `git diff` | **차이** 보기 | unstaged / `--cached` |
| `git pull` | 가져와 **병합** | fetch + merge |
| `git push` | 원격에 **반영** | 로컬 commit을 서버로 |

## 자주 헷갈리는 것 정리

| 구분 | 기억법 |
|------|--------|
| `init` vs `clone` | init = 빈 repo / clone = 있는 repo 복사 |
| `fetch` vs `pull` | fetch = 받기만 / pull = 받고 + 합치기 |
| `pull` vs `push` | pull = 당김 / push = 올림 |
| `diff` vs `diff --cached` | add 전 / add 후 |
