## 유형 1. 개념 O/X

> **목표:** 틀리면 안 되는 **브랜치·merge** 개념. ( O / X )

---

### 1-1
**문제:** Git **브랜치(branch)** 는 특정 **commit을 가리키는 이동 가능한 이름(줄기)** 이다. ( O / X )

**정답:** **O**

**해설:** PDF "Git Branching". 브랜치는 파일 폴더가 아니라 **commit 히스토리의 한 줄**입니다.

---

### 1-2
**문제:** `git branch feature`만 실행하면 `feature` 브랜치가 **생성**된다. ( O / X )  
`feature`로 **자동 이동**한다. ( O / X )

**정답:** **O** / **X**

**해설:** `branch` = **만들기만** · 이동 = `checkout`(또는 `switch`).

---

### 1-3
**문제:** `master`에서 갈라진 `feature`를 merge할 때, `master`가 **feature의 commit을 그대로 앞으로 당기기만** 하면 되는 경우를 **fast-forward merge**라고 한다. ( O / X )

**정답:** **O**

**해설:** `master`에 **새 commit이 없고** `feature`만 앞서 있으면 merge commit 없이 **포인터만 이동**합니다.

---

### 1-4
**문제:** 두 브랜치가 **같은 파일의 같은 부분**을 서로 다르게 수정하면 merge 시 **충돌(conflict)** 이 난다. ( O / X )

**정답:** **O**

**해설:** 충돌 파일에 `<<<<<<<`, `=======`, `>>>>>>>` 표시가 생깁니다.

---

### 1-5
**문제:** `origin/main`은 원격 `origin`의 `main` 브랜치를 가리키는 **추적(remote-tracking) 브랜치**이다. ( O / X )

**정답:** **O**

**해설:** `git fetch origin` 후 `origin/main`이 **원격 main의 로컬 복사본**으로 갱신됩니다.

---

### 1-6
**문제:** `git merge feature`는 **`feature` 브랜치**에 현재 브랜치 내용을 합친다. ( O / X )

**정답:** **X**

**해설:** merge는 **현재 checkout된 브랜치**에 `feature`를 **합침**. 방향이 반대입니다.

---

### 1-7
**문제:** `git branch -d feature`와 `git push origin --delete feature`는 **같은 종류**(로컬/원격)의 브랜치를 삭제한다. ( O / X )

**정답:** **X**

**해설:** `-d` = **로컬** 삭제 · `push --delete` = **원격** 삭제.

---

### 1-8
**문제:** `git fetch origin`은 원격 브랜치 정보만 갱신하고, `git pull`은 가져온 뒤 **merge까지** 한다. ( O / X )

**정답:** **O**

**해설:** `pull` ≈ `fetch` + `merge`. `origin/main` 등 추적 브랜치만 바뀌는 건 **fetch**.

---

### 1-9
**문제:** `origin`과 `origin/main`은 같은 것을 가리킨다. ( O / X )

**정답:** **X**

**해설:** `origin` = 원격 저장소 **별칭** · `origin/main` = 그 원격의 `main` **추적 브랜치**.

---

### 1-10 (`checkout` 두 가지 쓰임)
**상황:**

```bash
git checkout feature          # 브랜치 이동
git checkout -- file.txt      # 수정 폐기 (5-1 · 5-3)
# 아래와 **같은 의미**:
git checkout HEAD -- file.txt
```

**문제:** `git checkout feature`는 **브랜치 이동**, `git checkout -- file`은 **작업 폴더 수정 폐기**다. ( O / X )

**정답:** **O**

**해설 — HEAD 는 어디 갔나?**

**`git checkout HEAD -- file`** = **HEAD(마지막 commit)** 내용으로 파일 복원 (`5-1` `1-6`).

**`git checkout -- file`** 도 **같은 일** · HEAD 를 **생략한 짧은 표기** (시험·Lab 에서 둘 다 나옴).

| 명령 | 의미 |
|------|------|
| **`checkout -- file`** | HEAD 버전으로 되돌림 (**HEAD 생략**) |
| **`checkout HEAD -- file`** | **명시적으로** HEAD 버전으로 되돌림 |

**`--` 의 역할 (두 경우 다름):**

| | `checkout feature` | `checkout -- file` |
|--|-------------------|-------------------|
| `feature` / `file` | **브랜치 이름** | **파일 경로** |
| **`--`** | 없음 | “뒤는 **파일**” (브랜치 이름 `feature` 와 **구분**) |

→ `reset HEAD -- file` 은 HEAD 를 **항상 씀** · `checkout` 은 **`-- file` 만** 써도 됨.

---

### 1-11
**문제:** `git branch`와 `git checkout`은 둘 다 **브랜치를 만든다**. ( O / X )

**정답:** **X**

**해설:** `branch` = **만들기** · `checkout` = **이동**(또는 `-b`로 만들면서 이동).

---

### 1-12
**문제:** merge **충돌 중**에도 `git commit` 없이 merge가 **자동으로 완료**된다. ( O / X )

**정답:** **X**

**해설:** 충돌 해결 → `add` → `commit`으로 merge commit을 **직접** 완료해야 합니다.

---

## 유형 2. 명령·옵션 빈칸

> **「이런 일을 할 때 빈칸에 뭐?」**

---

### 2-1
**상황:** 현재 존재하는 **모든 브랜치 목록**을 보고, `*` 로 현재 브랜치를 확인.

```bash
git ______
```

**정답:** `branch`

**해설:** `* master`처럼 현재 브랜치에 `*`가 붙습니다.

---

### 2-2
**상황:** `experimental`이라는 **새 브랜치만** 만든다. (아직 이동하지 않음)

```bash
git ______ experimental
```

**정답:** `branch`

---

### 2-3
**상황:** 작업 브랜치를 `experimental`로 **이동**한다.

```bash
git ______ experimental
```

**정답:** `checkout`

**해설:** (요즘 Git: `git switch experimental`도 가능, 강의·5-1은 `checkout`)

---

### 2-4
**상황:** `experimental`에서 작업·commit을 마쳤다. **`master`로 돌아와** `experimental`의 변경을 **합친다**.

```bash
git checkout master
git ______ experimental
```

**정답:** `merge`

**해설:** merge는 **현재 브랜치(master)** 에 다른 브랜치 내용을 **합침**.

---

### 2-5
**상황:** 브랜치가 **갈라졌다 합쳐진** 모습을 로그에서 보고 싶다.

```bash
git log ______
```

**정답:** `--graph`

**해설:**

| 옵션 | 역할 |
|------|------|
| **`--graph`** | commit 히스토리를 **가지·합류 그림**(`*`, `|`, `\`)으로 표시 · **갈라졌다 합쳐진** 모습 (`6-7`) |
| **`--oneline`** | commit **한 줄** 요약 (hash 앞 7자 + 메시지 · `5-1` `6-4`) |

**자주 같이 씀:**

```bash
git log --graph --oneline
```

**예 (merge 전·후 느낌):**

```
# --oneline 만
a1b2c3d Merge branch 'feature'
9f8e7d6 feature work
3c2b1a0 main work

# --graph --oneline (가지 보임)
*   a1b2c3d Merge branch 'feature'
|\
| * 9f8e7d6 feature work
* | 3c2b1a0 main work
```

→ 이 문제 빈칸 = **그림**이 필요하니 **`--graph`** · 보기 좋게 하려면 **`--oneline` 추가**.

---

### 2-6
**상황:** 현재 브랜치 이름을 `main`으로 **바꾼다**. (강제)

```bash
git branch ______ main
```

**정답:** `-M`

**해설:** `-m` (move) · `-M` (move **force**). 5-1 §2-15와 동일.

---

### 2-7
**상황:** merge가 끝난 **`old-feature` 브랜치**를 **로컬에서 삭제**한다. (이미 merge됨)

```bash
git branch ______ old-feature
```

**정답:** `-d`

**해설:** `-d` = delete (merged면). **강제** 삭제는 `-D`.

---

### 2-8
**상황:** 원격 `origin`의 최신 브랜치 정보를 **로컬의 `origin/main` 등**으로 갱신만 한다.

```bash
git ______ origin
```

**정답:** `fetch`

**해설:** fetch 후 `origin/main`이 업데이트됩니다. 작업 폴더 자동 merge는 **pull** 때.

---

### 2-9
**상황:** 로컬 `main`을 push하면서 **`origin/main`과 연결**(upstream)한다. (첫 push)

```bash
git push ______ origin main
```

**정답:** `-u`

**해설:** `-u` = `--set-upstream` · 이후 `git pull`/`git push`만으로도 추적 가능.

---

### 2-10
**상황:** 원격 `origin`에 있는 **`old-feature` 브랜치**를 **서버에서 삭제**한다.

```bash
git push origin ______ old-feature
```

**정답:** `--delete` (또는 `:old-feature` 형식 — 시험은 `--delete` 위주)

**해설:** **로컬** `git branch -d`와 다름 — 이건 **원격** 브랜치 삭제.

---

### 2-11 (명령 ↔ 역할)
**문제:** 빈칸에 **역할 한 줄**을 쓰시오.

| 명령 | 역할 (빈칸) |
|------|-------------|
| `git branch` | |
| `git branch feature` | |
| `git checkout feature` | |
| `git merge feature` | |
| `git branch -d feature` | |
| `git fetch origin` | |
| `git push -u origin main` | |
| `git push origin --delete old` | |

**정답:**

| 명령 | 역할 (시험에 적을 분량) |
|------|-------------------------|
| `git branch` | 브랜치 **목록** (`*` = 현재 브랜치) |
| `git branch feature` | `feature` 브랜치 **생성** (이동 X) |
| `git checkout feature` | `feature` 브랜치로 **이동** |
| `git merge feature` | **현재 브랜치**에 `feature` 내용 **병합** |
| `git branch -d feature` | merge된 **로컬** 브랜치 **삭제** |
| `git fetch origin` | 원격 브랜치 정보 **갱신** (`origin/main` 등) |
| `git push -u origin main` | push + **upstream(추적)** 설정 |
| `git push origin --delete old` | 원격 **`old` 브랜치 삭제** |

**로컬 vs 원격 브랜치 삭제**

| 목적 | 명령 |
|------|------|
| 로컬 브랜치 삭제 | `git branch -d 이름` |
| 원격 브랜치 삭제 | `git push origin --delete 이름` |

---

### 2-12
**상황:** `feature` 브랜치를 **만들면서 동시에 이동**한다.

```bash
git ______ -b feature
```

**정답:** `checkout` (또는 `switch -c`)

**해설:**

```bash
git checkout -b feature
#            ↑
#            -b = **b**ranch (새 브랜치 **만들면서** 이동)
```

| 명령 | 하는 일 |
|------|---------|
| **`git branch feature`** | 브랜치 **만들기만** (이동 **안 함** · `1-11`) |
| **`git checkout -b feature`** | 브랜치 **만들고** + 그 브랜치로 **이동** (이 문제) |
| **`git checkout feature`** | **이미 있는** 브랜치로 **이동만** (`1-10`) |

**`-b`** = **b**ranch · “**새 branch** 만들어라” 옵션.

(최신 Git: `git switch -c feature` — **c**reate 와 비슷한 역할)

---

### 2-13
**상황:** merge **안 된** 로컬 브랜치를 **강제** 삭제한다.

```bash
git branch ______ feature
```

**정답:** `-D`

**해설:** `-d` = 안전 삭제(merge됨) · `-D` = **강제** 삭제.

## 유형 4. 순서·로직 빈칸

> **알고리즘·워크플로 순서** (공지: coding algorithms)

---

### 4-1
**문제:** `experimental` 브랜치에서 기능 개발 후 `master`에 합칠 때 **단계 번호** (1~5).

```
( ) git merge experimental
( ) git branch experimental
( ) git checkout master
( ) git checkout experimental
( ) (experimental에서 작업 후 commit)
```

**정답:**  
1. `git branch experimental`  
2. `git checkout experimental`  
3. (작업 후 commit)  
4. `git checkout master`  
5. `git merge experimental`

**해설:** **만들기 → 이동 → 작업 → master로 → merge**

---

### 4-2
**문제:** merge **충돌(conflict)** 해결 **4단계** 순서.

**정답:**  
1. 충돌 파일 **수동 편집** (`<<<<<<<` 등 제거)  
2. **`git add`** (해결된 파일 스테이징)  
3. **`git commit`** (merge 완료)  
4. (필요 시) **`git push`**

**해설:** PDF "Basic Merge Conflicts". 충돌 중에는 merge commit **미완료** 상태.

---

### 4-3
**상황:** `master`와 `feature` **둘 다** merge 이후 새 commit이 있음. `master`에서 `git merge feature` 실행.

**문제:** **fast-forward**만 일어나는가? (O/X) **merge commit**이 생기는가? (O/X)

**정답:** fast-forward **X** · merge commit **O**

**해설:** 양쪽 모두 앞서 있으면 **3-way merge** + merge commit. fast-forward는 **한쪽만** 앞설 때.

---

### 4-4
**문제:** merge conflict 파일에 나타나는 **세 기호**를 **순서대로** 쓰시오.

**정답:** `<<<<<<<` · `=======` · `>>>>>>>`

**해설:** `<<<<<<< HEAD` = 현재 브랜치 · `=======` = 구분 · `>>>>>>> branch` = 합치려는 브랜치.

---

## 유형 5. 상태·메시지 예측

> **`git branch` / merge 후 HEAD·브랜치 상태** (공지: command outcomes)

---

### 5-1
**상황:**

```bash
git branch feature
git checkout feature
# feature에서 file.txt 수정 후 commit
git checkout master
git merge feature
```

(`master`에 feature 분기 **이후** 추가 commit **없음**)

**문제:** merge 후 `master`와 `feature`가 **같은 commit을 가리키게** 되는가? (fast-forward) (O/X)

**정답:** **O**

**해설:** fast-forward → `master`가 `feature` 끝으로 **이동**합니다.

---

### 5-2
**상황:** `master`와 `feature` **둘 다** 같은 파일 같은 줄을 **다르게** 수정한 뒤 `git merge feature` 실행.

**문제:** merge가 **자동으로 바로 완료**되는가? (O/X)  
충돌 파일에 **`<<<<<<<`** 표시가 생기는가? (O/X)

**정답:** **X** / **O**

**해설:** 충돌 해결 → `add` → `commit`으로 merge commit 완료.

---

### 5-3
**상황:** `git checkout feature` 후 `git status` — working tree clean.

**문제:** `git branch` 출력에서 `*` 는 **어느 브랜치** 옆에 붙는가?

**정답:** **`feature`**

**해설:** `*` = **현재 checkout된 브랜치** (HEAD가 가리키는 브랜치).

---

### 5-4
**상황:** 아래를 순서대로 실행했다.

```bash
git branch dev
git checkout dev
echo "new" >> app.txt && git add app.txt && git commit -m "on dev"
git checkout main
git merge dev
```

(`main`은 `dev` 분기 **이후** 추가 commit **없음**)

**문제:**  
(1) `git branch dev` 직후 HEAD는 **dev** / **main** 중 어디?  
(2) merge 후 **fast-forward** 인가? (O/X)  
(3) `git branch`에서 `*` 는 **main** 옆인가? (O/X)

**정답:**  
(1) **main** (branch만 만들고 checkout 안 함)  
(2) **O**  
(3) **O** (`checkout main` 후 merge했으므로)

**해설:** `branch` ≠ `checkout`.

---

### 5-5
**상황:** non-fast-forward merge 후 `git status` — 충돌 해결·`add`·`commit` **완료**.

**문제:** `git branch`에서 `*` 는 **merge를 실행한 브랜치**(예: `master`) 옆인가? (O/X)

**정답:** **O**

**해설:** merge는 **현재 checkout된 브랜치**에서 실행 · 완료 후에도 HEAD는 그 브랜치에 머무름.

## 유형 6. diff·log 출력 예측

> **명령 실행 시 log·충돌 파일 결과** (공지: outcomes)

---

### 6-1 (`log --graph` · merge **전**)
**상황:** `master` 와 `feature` 가 **갈라진 뒤** · **아직 merge 안 함** · 지금 **`feature` 브랜치**에 있음 (HEAD = `feature` 끝).

**무슨 일이 있었나:**

| 순서 | 일 |
|------|-----|
| 1 | `master`: commit `A` → `B` → `C` |
| 2 | `C` 에서 `feature` 브랜치 생성 |
| 3 | `feature` 에서 commit `E` (`add feature`) |
| 4 | `master` 로 돌아가 commit `D` (`fix on master`) |
| 5 | **merge 아직 안 함** |

**그림 (아래 = 예전 · 위 = 최신):**

```
      master:  A --- B --- C --- D
                            \
      feature:                E   ← 지금 여기 (HEAD)
```

**`git log --graph --oneline` 이면 대략:**

```
* eeeeee add feature          ← feature 끝 (HEAD *)
| * ddddd fix on master       ← master 끝
|/
* ccccc common base
* bbbbb
* aaaaa
```

**문제:**

(1) 위처럼 **가지**(`|`, `/`) 와 **`*`(현재 위치)** 가 출력에 나타나는가? ( O / X )

(2) `master` 와 `feature` 가 **같은 commit 한 줄**에 있는가? ( O / X )

**정답:** (1) **O** · (2) **X**

**해설:**

| 질문 | 이유 |
|------|------|
| (1) **O** | **`--graph`** = 갈라짐·합류 **그림** · `*` = **HEAD**(지금 `feature`) |
| (2) **X** | `master` 끝 = **`D`** · `feature` 끝 = **`E`** · **서로 다른 commit** |

→ merge **후**에야 한 줄로 모일 수 있음 (`6-3` fast-forward).

---

### 6-2
**상황:** `master`와 `feature`가 `readme.txt` **같은 줄**을 각각 `"A"`, `"B"`로 수정한 뒤 `master`에서 `git merge feature` → **충돌**.

**문제:** `readme.txt`에 나타나는 **세 구분 기호**를 순서대로 쓰고, `=======` **위쪽**이 **HEAD(현재 브랜치)** 쪽인가? (O/X)

**정답:** `<<<<<<<` · `=======` · `>>>>>>>` / **O**

**해설:** `<<<<<<< HEAD` 아래 = **master(현재)** 내용 · `>>>>>>> feature` 위 = **feature** 내용.

---

### 6-3 (`fast-forward` merge **직후** · `6-1` 과 **반대**)
**상황:** `6-1` 은 `master`·`feature` 가 **둘 다** 새 commit 이 있어 **갈라진** 상태였음 · 여기선 **`master`는 그대로** · `feature` 만 앞서 있음.

**무슨 일이 있었나:**

| 순서 | 일 |
|------|-----|
| 1 | `master`: `A` → `B` → `C` |
| 2 | `C` 에서 `feature` 생성 |
| 3 | `feature` 에만 `D` → `E` 추가 |
| 4 | **`master` 는 `C` 에 그대로** (새 commit **없음** · `1-3`) |
| 5 | `git checkout master` 후 `git merge feature` → **fast-forward** |

**merge 전:**

```
master:  A --- B --- C
                      \
feature:               D --- E
```

**fast-forward merge 직후** (`master` 포인터만 `E` 로 **당겨짐** · merge commit **없음**):

```
master:  A --- B --- C --- D --- E
feature:                       E   ← 둘 다 같은 commit
```

**`git log --graph --oneline` 예:**

```
* eeeee (HEAD -> master, feature) add feature
* ddddd more feature work
* ccccc common base
```

→ **`master`**, **`feature`** 이름이 **같은 줄**에 같이 붙을 수 있음.

**문제:**

(1) `git log --oneline -3` 기준 · `master` 와 `feature` **끝 commit hash** 가 **같은가**? ( O / X )

(2) `git log --graph --oneline` 에서 두 브랜치 이름이 **같은 commit 한 줄**에 붙을 수 있는가? ( O / X )

**정답:** (1) **O** · (2) **O**

**해설:**

**`-3` 이 뭐야?**

```bash
git log --oneline -3
#                 ↑
#                 **최근 commit 3개만** 출력 (`-n 3` 과 같음)
```

| 옵션 | 역할 |
|------|------|
| **`--oneline`** | commit **한 줄** 요약 (`5-1` `6-4`) |
| **`-3`** | **가장 최근 3개** commit 만 보여 줌 (전체 log 아님) |

**예 (이 상황 · 맨 위가 최신):**

```
eeeeee (HEAD -> master, feature) add feature   ← 1번째 (가장 최신)
dddddd more feature work                       ← 2번째
cccccc common base                             ← 3번째
# 그 아래 A, B 는 -3 이라 **안 나옴**
```

→ (1) 질문은 **맨 위(최신) commit** 의 hash 를 `master`·`feature` 가 **같이 가리키냐**는 뜻.

| | **`6-1` (merge 전)** | **이 문제 (fast-forward 후)** |
|--|----------------------|-------------------------------|
| `master` 끝 | `D` | **`E`** |
| `feature` 끝 | `E` | **`E`** |
| hash 같음? | **X** | **O** |
| 한 줄에 두 브랜치? | **X** | **O** |

→ fast-forward = `master` 가 `feature` 끝으로 **포인터만 이동** · **같은 commit** 을 가리킴 (`4-3`).
