## 1. 개념·OX (Part 3 PDF)

### 1-1
**묻는 것:** Git **브랜치(branch)** 가 무엇인지

**문제:** 브랜치를 한 줄로 설명하시오.

**정답:** 특정 **commit을 가리키는 이동 가능한 이름(줄기)** — 여러 작업 줄기를 **갈라서** 진행할 수 있게 함

**해설:** PDF "Git Branching". 브랜치는 파일 폴더가 아니라 **commit 히스토리의 한 줄**입니다. `master`/`main`, `feature` 등이 브랜치 이름입니다.

---

### 1-2
**묻는 것:** `git branch feature`만 실행했을 때

**문제:** `feature` 브랜치가 **생성**되는가? (O/X)  
현재 작업 위치가 **자동으로** `feature`로 **이동**하는가? (O/X)

**정답:** **O** / **X**

**해설:** PDF "Basic Branching". `branch`는 **만들기만** 합니다. 이동은 **`git checkout feature`** (또는 `git switch feature`)가 필요합니다. 5-1 §4-3과 동일.

---

### 1-3
**묻는 것:** Fast-forward merge

**문제:** `master`에서 갈라진 `feature`를 merge할 때, `master`가 **feature의 commit을 그대로 앞으로 당기기만** 하면 되는 경우를 **fast-forward merge**라고 한다. ( O / X )

**정답:** **O**

**해설:** PDF "Basic Merging". `master`에 **새 commit이 없고** `feature`만 앞서 있으면, merge commit 없이 **포인터만 이동**합니다.

---

### 1-4
**묻는 것:** Merge conflict

**문제:** 두 브랜치가 **같은 파일의 같은 부분**을 서로 다르게 수정하면 merge 시 **충돌(conflict)** 이 난다. ( O / X )

**정답:** **O**

**해설:** PDF "Basic Merge Conflicts". 충돌 파일에 `<<<<<<<`, `=======`, `>>>>>>>` 표시가 생깁니다. 사람이 고친 뒤 `add` → `commit`으로 merge를 마칩니다.

---

### 1-5
**묻는 것:** 원격 브랜치 이름

**문제:** 원격 `origin`의 `main` 브랜치를 로컬에서 가리킬 때 흔히 쓰는 이름은?

**정답:** **`origin/main`** (또는 remote-tracking branch)

**해설:** PDF "Remote Branches". `git fetch origin` 후 `origin/main`이 **원격 main의 로컬 복사본(추적 브랜치)** 으로 갱신됩니다.

## 2. 명령·옵션 빈칸 채우기

> **「이런 일을 하려고 할 때, 빈칸에 뭐가 들어가야 할까?」**

---

### 2-1
**상황:** 현재 존재하는 **모든 브랜치 목록**을 보고, `*` 로 현재 브랜치를 확인하고 싶다.

**문제:** 빈칸에 들어갈 하위 명령은?

```bash
git ______
```

**정답:** `branch`

**해설:** `history 6.sh`의 `git branch`. `* master`처럼 현재 브랜치에 `*`가 붙습니다.

---

### 2-2
**상황:** `experimental`이라는 **새 브랜치만** 만든다. (아직 이동하지 않음)

**문제:** 빈칸을 채우시오.

```bash
git ______ experimental
```

**정답:** `branch`

**해설:** 5-1 §4-3. `git branch experimental` = 생성만.

---

### 2-3 (Switching Branches)
**상황:** 작업 브랜치를 `experimental`로 **이동**한다.

**문제:** 빈칸을 채우시오.

```bash
git ______ experimental
```

**정답:** `checkout`

**해설:** PDF "Switching Branches". (요즘 Git: `git switch experimental`도 가능, 강의·5-1은 `checkout`)

---

### 2-4 (Basic Merging)
**상황:** `experimental`에서 작업·commit을 마쳤다. **`master`로 돌아와** `experimental`의 변경을 **합친다**.

**문제:** 아래 빈칸 2개를 채우시오.

```bash
git checkout master
git ______ experimental
```

**정답:** `merge`

**해설:** PDF "Basic Branching and Merging". merge는 **현재 브랜치(master)** 에 다른 브랜치(experimental) 내용을 **합침**.

---

### 2-5
**상황:** 브랜치가 **갈라졌다 합쳐진** 모습을 로그에서 보고 싶다.

**문제:** 빈칸을 채우시오.

```bash
git log ______
```

**정답:** `--graph`

**해설:** 5-1 PDF·실습. `--oneline`과 함께 `git log --graph --oneline`으로 자주 씁니다.

---

### 2-6 (Branch Management — history 6)
**상황:** 현재 브랜치 이름을 `main`으로 **바꾼다**. (강제)

**문제:** 빈칸을 채우시오.

```bash
git branch ______ main
```

**정답:** `-M`

**해설:** `history 6.sh`: `-m` (move), `-M` (move force). 5-1 §2-16과 동일.

---

### 2-7
**상황:** merge가 끝난 **`old-feature` 브랜치**를 **로컬에서 삭제**한다. (이미 merge됨)

**문제:** 빈칸을 채우시오.

```bash
git branch ______ old-feature
```

**정답:** `-d`

**해설:** PDF "Branch Management". `-d` = delete (merged면). 강제 삭제는 `-D`.

---

### 2-8 (Remote Branches)
**상황:** 원격 `origin`의 최신 브랜치 정보를 **로컬의 `origin/main` 등**으로 갱신만 한다.

**문제:** 빈칸을 채우시오.

```bash
git ______ origin
```

**정답:** `fetch`

**해설:** PDF "Remote Branches". 5-1·5-3. fetch 후 `origin/main`이 업데이트됩니다. 작업 폴더 자동 merge는 **pull** 때.

---

### 2-9 (Tracking Branches)
**상황:** 로컬 `main`을 push하면서 **`origin/main`과 연결**(upstream)한다. (첫 push)

**문제:** 빈칸을 채우시오.

```bash
git push ______ origin main
```

**정답:** `-u`

**해설:** PDF "Tracking Branches". 5-1 §2-17, 5-2 §2-3. 이후 `git pull`/`git push`만으로도 추적 가능.

---

### 2-10 (Deleting Remote Branches)
**상황:** 원격 `origin`에 있는 **`old-feature` 브랜치**를 **서버에서 삭제**한다.

**문제:** 빈칸을 채우시오.

```bash
git push origin ______ old-feature
```

**정답:** `--delete` (또는 `:old-feature` 형식 — 시험은 `--delete` 위주)

**해설:** PDF "Deleting Remote Branches". **로컬** `git branch -d`와 다름 — 이건 **원격** 브랜치 삭제.

## 3. 결과 예측 — 브랜치·merge

### 3-1
**상황:**

```bash
git branch feature
git checkout feature
# feature에서 file.txt 수정 후 commit
git checkout master
git merge feature
```

**문제:** `master`와 `feature`가 **같은 commit을 가리키게** 되는가? (fast-forward인 경우) (O/X)

**정답:** **O**

**해설:** `master`에 feature 분기 이후 **새 commit이 없었다면** fast-forward → `master`가 `feature` 끝으로 **이동**합니다.

---

### 3-2
**상황:** `master`와 `feature` **둘 다** 같은 파일 같은 줄을 **다르게** 수정한 뒤 `git merge feature` 실행.

**문제:** merge가 **자동으로 바로 완료**되는가? (O/X)  
충돌 파일에 **`<<<<<<<`** 표시가 생기는가? (O/X)

**정답:** **X** / **O**

**해설:** PDF "Basic Merge Conflicts". 충돌 해결 → 파일 수정 → `git add` → `git commit`으로 merge commit 완료.

---

### 3-3
**상황:** `git checkout feature` 후 `git status` — working tree clean.

**문제:** `git branch` 출력에서 `*` 는 **어느 브랜치** 옆에 붙는가?

**정답:** **`feature`**

**해설:** `*` = **현재 checkout된 브랜치** (HEAD가 가리키는 브랜치).

## 4. 순서·워크플로

### 4-1
**상황:** PDF "Basic Branching and Merging" — `experimental` 브랜치에서 기능 개발 후 `master`에 합친다.

**문제:** 아래 단계에 번호를 매기시오.

```
( ) git merge experimental
( ) git branch experimental
( ) git checkout master
( ) git checkout experimental
( ) (experimental에서 작업 후 commit)
```

**정답:**  
1. `git branch experimental`  
2. `git checkout experimental`  
3. (작업 후 commit)  
4. `git checkout master`  
5. `git merge experimental`

**해설:** 5-1 §4-3과 동일. **만들기 → 이동 → 작업 → master로 → merge**

---

### 4-2
**상황:** merge **충돌**이 난 뒤 해결하는 순서.

**문제:** 올바른 순서 4단계를 쓰시오.

**정답:**  
1. 충돌 파일 **수동으로 편집** (`<<<<<<<` 등 제거)  
2. **`git add`** (해결된 파일 스테이징)  
3. **`git commit`** (merge commit 완료)  
4. (필요 시) **`git push`**

**해설:** PDF "Basic Merge Conflicts". 충돌 중에는 merge commit이 **완료되지 않은** 상태입니다.

## 5. 표 완성 (Part 3 핵심)

**문제:** 설명 칸을 채우시오.

| 명령 | 설명 (빈칸) |
|------|-------------|
| `git branch` | |
| `git branch feature` | |
| `git checkout feature` | |
| `git merge feature` | |
| `git branch -d feature` | |
| `git fetch origin` | |
| `git push -u origin main` | |
| `git push origin --delete old` | |

---

**정답·해설**

| 명령 | 설명 (시험에 적을 분량) |
|------|-------------------------|
| `git branch` | 브랜치 **목록** (`*` = 현재 브랜치) |
| `git branch feature` | `feature` 브랜치 **생성** (이동 X) |
| `git checkout feature` | `feature` 브랜치로 **이동** |
| `git merge feature` | **현재 브랜치**에 `feature` 내용 **병합** |
| `git branch -d feature` | merge된 **로컬** 브랜치 **삭제** |
| `git fetch origin` | 원격 브랜치 정보 **갱신** (`origin/main` 등) |
| `git push -u origin main` | push + **upstream(추적)** 설정 |
| `git push origin --delete old` | 원격 **`old` 브랜치 삭제** |

**로컬 vs 원격 브랜치 삭제**

| 목적 | 명령 |
|------|------|
| 로컬 브랜치 삭제 | `git branch -d 이름` |
| 원격 브랜치 삭제 | `git push origin --delete 이름` |

## 6. 종합 (시험 스타일)

**상황:** 아래를 순서대로 실행했다.

```bash
git branch dev
git checkout dev
echo "new" >> app.txt && git add app.txt && git commit -m "on dev"
git checkout main
git merge dev
```

(`main`은 `dev` 분기 **이후** 추가 commit **없음**)

**문제:**  
(1) `git branch dev` 직후 HEAD는 **dev** / **main** 중 어디?  
(2) merge 후 **fast-forward** 인가? (O/X)  
(3) `git branch`에서 `*` 는 **main** 옆인가? (O/X)

**정답:**  
(1) **main** (branch만 만들고 checkout 안 함)  
(2) **O**  
(3) **O** (`checkout main` 후 merge했으므로)

**해설:** 2-2·2-3·3-1 패턴. `branch` ≠ `checkout`.

## 자주 헷갈리는 것 (5-4)

| 헷갈림 | 정리 |
|--------|------|
| `git branch` vs `git checkout` | **만들기** vs **이동** |
| `git merge A` | **현재 브랜치**에 A를 합침 (A에 merge하는 게 아님) |
| `origin` vs `origin/main` | **원격 별칭** vs **원격 main의 추적 브랜치** |
| `branch -d` vs `push --delete` | **로컬** 삭제 vs **원격** 삭제 |
| `fetch` vs `pull` | 원격 브랜치 정보만 vs 가져와 **merge** |
| `checkout 브랜치` vs `checkout -- 파일` | **브랜치 이동** vs **파일 수정 폐기** (5-1) |
